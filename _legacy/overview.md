## 没有审核怎么真实运行

这是本轮的核心答案：**把链条两端各换一端，中间四段不动**。

| 环节 | 真假 | 说明 |
|---|---|---|
| 数据 | 真 | 评论快照来自真实评论导出，字段结构与接口返回一致 |
| 判定 / 风控 / 生成 | 真 | 一行没改，原样跑 |
| 投递 / 到达 | 真 | 真的发出去，真的收到 |
| 终点 | **假** | 本该发到抖音评论区，改发到企微群 / QQ 群 / 本地文件 |

三条出口：`LocalOutlet`（零配置）、`WebhookOutlet`（建群加机器人，3 分钟）、
`OneBotOutlet`（NapCat 发 QQ 群）。

实测：11 条评论 → 6 条投递成功、2 条拦截、3 条沉默、0 条无草稿。

**不做的**：不往任何真实抖音用户那里发消息。没审核就没有发送权限，
绕过去是违规，不是技术问题。

## 阶段规划（M0–M5）

每个阶段都是能独立验收的小闭环，不是"写了一半的模块"。

| 阶段 | 目标 | 验收门槛 |
|---|---|---|
| **M0** 演示闭环 | 跑到手机能收到 | 已完成：四类结局齐全，群收到 6 条 |
| **M1** 判定校准 | 量出「该回 / 不该回」的准确率 | 100 条真实评论，与人工标注一致率 ≥ 80% |
| **M2** 生成质量 | 草稿达到「愿意直接发」 | 抽 20 条，至少 12 条原样发出（采纳率 60%） |
| **M3** 真实接入 | 换真接口，只读一周 | 连续 7 天不漏、不重、不自回自答，有告警 |
| **M4** 分级放权 | 让系统自己挣发送权 | 自动占比升、驳回率不升 |
| **M5** 规模化 | 第二个账号、第二个平台 | 新增账号只改配置，不改 `gateway.py` |

**顺序不能换**：先证明判断对（M1），再证明话说得好（M2），最后才给发送权（M4）。
反过来做，会出现"系统每天在发消息，但没人知道多少条是错的"这种状态。

## 「被 @」改成「尽量回复」，判定层跟着变了

需求从「被 @ 就自动回」改成「评论区提到我的人尽量回」，不只是措辞。

原来被提及直接返回满分，等于强制回复——那意味着「@我 6」也会发出去，
在公开评论区这比不回更像机器人。

现在改成 +0.65 高权重并豁免两项扣分（未被点名、刚回复过）。实测：

| 评论 | 分数 | 结局 |
|---|---|---|
| @我 这个多少钱 | 1.00 | 回复 |
| @我 承重多少 | 1.00 | 回复 |
| @我 能便宜点吗 | 1.00 | **拦截**（风控层，不是判定层） |
| @我 好看 | 0.65 | 回复 |
| @我 贵 | 0.45 | 观望 |
| @我 6 / @我 嗯 | 0.00 | 沉默 |

第三行是关键：**判定管「该不该开口」，风控管「能不能说这句」**。
合并成一层，就会出现「因为怕报价，所以连问价都不回」。

## 「被 @」在平台上的边界（不变）

抖音互动管理只有四个接口，全部以 `item_id` 为入口。**没有「@我的」消息流，没有 webhook。**

- 能覆盖：评论区里 @ 我的人（遍历自己作品评论 + 文本匹配）
- 覆盖不了：发布视频时 @ 我的人、点赞收藏通知、别人视频下提到我
- 硬上限：`/video/list/` 最多 80 条作品，超过的拉不到

## 微信 vs 抖音：先做哪个

「微信自动回复」落到实处是**企业微信自建应用**，不是个人微信。
个人号被腾讯安全中心的外挂公告明确列出，封的是登录账号本身。

| 渠道 | 官方支持 | 资质 | 开发量 | 拿到资格 |
|---|---|---|---|---|
| 企业微信自建应用 | 是 | 企业 / 个体户 | 2–3 天 | 当天 |
| 抖音评论回复 | 是 | 应用审核 | 已完成 | 2–3 工作日 |
| QQ + NapCat | 否 | 无 | 1 天 | 当天 |
| 微信个人号 | 明确禁止 | — | — | — |

### 现有代码复用度

Hub、判定、分级放权、持久化——**0 行改动**，注册时传 `channels=["wecom"]` 即可。
新增的三个文件已经写完并验证：

- `wecom_crypto.py`：AES-256-CBC，用 FIPS-197 和企业微信官方样例两组向量确认
  （签名算出 `477715d1…f3e6`，明文与文档一致）
- `wecom.py`：客户端（令牌缓存）+ 适配器（内存队列，poll 不发请求）
- `wecom_server.py`：回调服务，5 秒窗口用「验签解密入队后立刻返回空」绕开

### 「抖音只做评论回复」省不了多少

接入占 15%，抖音那半已经做完。70% 的成本在判定和语料，与渠道无关。
现在的瓶颈是 M1（一致率 80%）和 M2（采纳率 60%），都是质量指标不是功能数量。

### 顺序

1. **企业微信跑通真实收发**（3–5 天）。它是唯一「不等审核 + 官方支持 + 能拿真实数据」的渠道
2. 同时提交抖音权限申请（2–3 工作日）
3. 权限下来后只换适配器，补 OAuth 和回调域名
4. 然后才是 M1 校准——之前不该开自动发送

### 企业微信的三个限制

只能发给企业成员（外部客户要「微信客服」，另一套接口）、回调必须公网可达、
真实聊天语态和评论区差别大，语料基本要重写。

验证建议用两个号对聊：一个当客服一个当顾客，不需要外部客户。

### 注册入口：手机也行，但建应用要回电脑

两个入口都能注册：电脑 `work.weixin.qq.com` → 右上角「企业注册」；
手机微信搜「企业微信」公众号 → 底部「联系我们」→「立即注册」。

差别在于：**建应用、配回调都在管理后台**，而手机端后台功能不全。
所以手机注册完仍要用电脑扫码登录后台。要填的只有企业名称、行业、人数、
管理员姓名和手机号——企业名称可以自拟，用自己的名字加个「工作室」就行。

### 注册不需要营业执照（本轮核实）

腾讯客服原文支持个人注册企业微信；管理后台里不验证主体也能建自建应用、
配接收消息。真正卡人的是**回调域名必须与企业认证主体一致**——
没营业执照就没有认证主体，域名配不上。

官方对未认证企业给的绕法是：**回调地址直接填 IP 形式**，
`http://1.2.3.4:8780/wecom/callback`，再用同一个 IP 配「企业可信 IP」。

抖音没有这个退路，它的 OAuth 回调必须是已备案域名。这是两边门槛的真正差别。

### 没有资质也能跑通全链路（wecom_sim.py）

一条命令，不需要注册、不需要公网、不联网：

```bash
python wecom_sim.py
```

它本地起两个服务：一个冒充 `qyapi.weixin.qq.com`，一个跑真实的回调代码。
消息按真实协议加密、签名后 POST 过来，走的是真 HTTP 和真 AES。

实跑结果：推送 10 条 → 入队 10 条 → 假平台收到 7 条 → 拦截 2 条 → 沉默 1 条。
六项自检全过：URL 验证、消息到达、确实发出、边界拦截、令牌缓存、重复去重。

**它不替换 transport**——替换了能测业务逻辑，但测不到 URL 编码、CDATA、
Content-Type、端口绑定，而这些恰恰是真实部署第一天会出错的地方。

### 抖音授权：域名能绕，但权限才是真卡点

`redirect_uri` 是「浏览器跳去哪」，不是「回调服务器」。那个地址打不开也没关系——
授权成功后 code 已经在地址栏里了，复制出来本地换 token 就行。不需要公网、不需要备案。

```bash
python douyin_auth.py url --client-key tt... --redirect https://x.com/cb
python douyin_auth.py paste --client-key tt... --secret abc... --code "<整条 URL>"
```

粘裸码、整条 URL、带引号空格都能识别；`10007` 会提示「10 分钟且只能用一次」。

**但 2025-02 的公告把这事的优先级改了。** 抖音在 2025-02-13 停止接收移动/网站应用
申请 `item.comment`、`video.comment`、`data.external.item`，2025-03-13 起回收已开通的。
公告已生效一年半，新建的移动/网站应用申请不到评论权限——域名解决了也走不通。

所以「第三步最难」要改成「第四难」：
第一难有没有应用可申请，第二难评论权限批不批，第三难企业资质，域名排第四。

小程序是唯一不需要 redirect_uri 的官方通道（`tt.showDouyinOpenAuth` → ticket），
有独立接口 `list_comment`，但被标为「高级能力」，且 FAQ 有一句
「企业小程序和个人小程序目前均不支持获取粉丝数、评论数据」——字面读不出指统计还是内容。
**这个只能去控制台点一次才知道，不能把「文档里有」当成「你能批到」。**

### 交互式演示：能看出这是自动的

`wecom_sim.py` 跑一遍就退出，用来证明链路通，但看不出自动化。
`wecom_live.py` 是常驻的聊天窗口：

```bash
python wecom_live.py     # 打开 127.0.0.1:8790，打一句话，几百毫秒后自动回复
```

| 你说 | 结局 | 界面表现 |
|---|---|---|
| 在吗 | 自动回复 | 蓝色气泡 + 745ms + 放行原因 |
| 能便宜点吗 | 拦截 | 不产生气泡，居中提示「命中人设边界：便宜点」 |
| 嗯 | 不回复 | 居中提示「纯语气词，无信息量」 |

关键在第二行：**它不会回你**。会拒绝，才像有边界的东西。
走的是真协议（AES → 签名 → HTTP → 验签解密 → 判定 → 发送），
界面上的耗时是真实处理时间。

### 用视频评论做 M1：能测一半

同一条聊天消息，两套语料各跑一遍，差异落在哪一层很明确：

| | 结果 | 含义 |
|---|---|---|
| 判定一致 | 8/10 | 意图词表跨场合通用，**判定可校准** |
| 草稿可用 | 4/7（评论语料）vs 7/7（聊天语料） | 生成层不可迁移 |

最典型的一种错：私聊里被问「多少钱」，评论语料答「价格我私信你说」——
用户已经在私聊里了。

所以 M1 要拆成两个指标：

- **M1a 判定一致率**：可以用视频评论做，现在就能开始
- **M1b 草稿采纳率**：必须用目标场合的真实记录，评论数据替代不了

评论数据能把「该不该回」校准到可用，「回得好不好」完全不行。

## 人设配置层：判定与商品解耦

原来的判定绑在「卖木工桌」上——`necessity.py` 里硬编码着「求链接 / 在哪买 / 价格」。
换商品勉强能用，换赛道直接失效：做内容的账号被问「求链接」，系统还以为来了生意。

拆成两层：

| | 意图层（跨行业固定） | 素材层（每账号一份） |
|---|---|---|
| 内容 | purchase / inquiry / after_sales / social / negative | 词表、答案库、风格样本、边界 |
| 谁改 | 不改代码 | 改 JSON |

判定只认意图标签，代码里再也找不到「求链接」三个字。

### 四种形态

`product`（卖货）/ `content`（做内容不卖）/ `service`（卖方案）/ `none`（个人号）。
`validate` 会检查矛盾：标了 content 却配购买词表，会把普通评论误判成商机。

### 怎么证明它通用

```bash
python persona_cli.py diff --a persona.json --b personas/creator.json
```

同一批 11 条评论，两份配置，**6 条结果不同**：

| 评论 | 电商 | 内容号 |
|---|---|---|
| 求链接 | 回复 0.90 | 沉默 0.00 |
| 承重多少 | 回复 0.90 | 无稿 0.60 |
| 这个多少钱 | 「价格我私信你说」 | 「我不卖东西哈，纯拍着玩」 |

最后一行是同一条评论、同一个引擎、两套回答。差别只在加载了哪份配置。

### 仍然不能复用的

语料（决定像不像人）、知识库（产品参数）、阈值（可沿用但要复测）。
能复用的只有「什么样的评论值得回」这个判断逻辑——但那本来就是最大的一块。

## 分级放权怎么工作

| 层 | 判什么 | 不过会怎样 |
|---|---|---|
| 话术风险 | 回复本身是否涉及价格 / 承诺 / 售后 | 永久人工，不参与解锁 |
| 置信度 | 消息有多明确在问价或求链接 | 进队列 |
| 信任额度 | 你对系统的历史采纳率（确认 +1 / 驳回 −2） | 进队列 |

---

## 关键判断

1. **控制台要验证的不是技术，是两件事**：你看不看得懂每条为什么被这样处理；
   你愿不愿意把草稿直接发出去。第二点决定项目成败。
2. **令牌是最容易断的地方。** access_token 15 天、refresh_token 30 天、有续期权 195 天。
3. **去重、限流、翻页上限防的不是平台，是自己。**
4. **改阈值只能止损，补语料才是提升。** 已三次验证（「这个在哪买」「质量怎么样」「多少钱」）。
5. **适配器只回答「技术上能不能发」。「该不该自己发」归 Hub 的三层闸门管。**
6. **资质比最初估计的乐观。** 官方能力页写「暂无准入条件，任一应用均可申请」，
   现实路径是「个人小程序 → 申请评论管理能力」。
7. **演示的可信度取决于假的那一段有多小。** 只剩「终点」是假的，其余全真。

## 下一步：M1 现在就能做

### 评论从哪来：三层抽样

**不能随便找一个平台的 100 条评论。** 判定被「账号卖什么、怎么说话」决定：
「求链接」在卖木工桌的账号下是转化机会，在搞笑视频下是噪声。
换一个无关账号的评论，测出来的是另一个分布。

评论不够 100 条时，分三层凑，但**分组统计、不合并**：

| 层 | 来源 | 补什么 | 建议 |
|---|---|---|---|
| own | 自己账号（B 站也行） | 真实场景 | 全部，60 条够 |
| similar | 同品类账号公开评论 | 购买意图样本 | 20–30 |
| unrelated | 无关内容评论区 | 验证不误伤 | 20–30 |

B 站评论能用，因为判定逻辑跨平台通用（问句/购买意图/议价/退款）。
不通用的是语料和阈值——那些是账号特定的。所以 B 站数据验证「方法合理」，
抖音账号到位后要用同一人设重跑，两次对比才知道迁移损失。

### 三步

1. **导出评论**（不需要接口权限）
   - 抖音电脑端 `creator.douyin.com` → 互动管理 → 评论管理
   - B 站 `member.bilibili.com` → 评论管理
   - 一行一条，不用整理；表格复制出的「昵称 + Tab + 评论」也能识别

2. **导入并盲标**
   ```bash
   cd app/gateway
   python label.py        # 浏览器打开 127.0.0.1:8771
   ```
   粘贴 → 导入 → 逐条点「该回 / 不该回 / 拿不准」。键盘 `1` `2` `3`，`Backspace` 回退。

3. **揭晓结果**，看一致率与混淆矩阵。

### 为什么标注时看不到系统判定

不是界面上藏了，是后端根本不返回（`state()` 在未揭晓时不带 `system` / `draft` 字段）。
先看见结论再标，一致率会虚高，那个数字就失去意义。

### 门槛

| 条件 | 结论 |
|---|---|
| 样本 ≥ 100 且一致率 ≥ 80% | 进 M2 |
| 样本 ≥ 100 但一致率 < 80% | 调语料和权重 |
| 样本 < 100 | 只当参考 |

置信区间不参与判定，它回答「这个数字有多不精确」。一致率 80% 时：

| 样本 | 95% 区间 |
|---|---|
| 30 | 63% – 90% |
| 60 | 68% – 88% |
| 100 | 71% – 87% |
| 200 | 74% – 85% |

100 条那行下界只有 71%——所以要「下界 ≥80%」得做到 88% 一致率，
那个门槛对首轮校准不现实。判定按 80% 卡，区间用来看能信到什么程度。

等审核期间可以做完 M0–M2：网络层可注入，换真接口时核心代码不用改。

**B 线（陪伴产品）** 与 A 线独立，可并行，基于 AIRI 的 MIT 代码。
