自动回复 & 获客 · 阶段规划 2026-11-11
Roadmap / 无审核前置运行

把四件事做真，只剩一件事假

没有经过平台审核，就不可能有「往抖音评论区发消息」的权限——这是规则问题，不是技术问题。 但一个系统要能演示、能验证、能说服人，并不需要那最后一步。 把数据、判定、生成、投递四段都做成真的，只把终点换掉， 它就是一个真在运行的系统，而不是一段录像。

01

哪一段可以真，哪一段必须假

演示的可信度取决于「假的那一段有多小」。现在的做法是把假的压到只剩一个动作。

Real
数据

评论快照来自真实评论导出。字段结构就是接口返回的结构，不是编的。

Real
判定与生成

风控、激活度打分、语料匹配、话术风险分级，全部原样跑，一行没改。

Real
投递与到达

消息真的发出去，真的到达。发到你的企微群 / QQ 群 / 本地文件。

唯一假的是终点：本该发到抖音评论区的那条回复，发到了你自己能收到的地方。

02

四条路径，按推荐度排

路径数据 → 终点风险
A 回放 + 本地文件零配置，python demo_run.py 直接跑。写完就能在终端看到全部结局。 评论快照 → JSONL 无
B 回放 + 群机器人建个群、加个机器人、拿一个 URL，三分钟。手机能收到消息。 评论快照 → 企微/钉钉/飞书群 无
C 回放 + QQ 群起一个 NapCat，用小号把消息发到自己的 QQ 群。展示效果最接近真实聊天。 评论快照 → QQ 群 低
D 公开接口读 + 群机器人直接抓网页版公开评论。数据最新，但要绕过请求签名。 网页公开接口 → 群 中

A 和 B 已经能用了。「回放」不等于「假数据」——快照里的每一条都是真实评论， 只是取了某一个时间点的切片。判定和生成对这份切片的反应，与对实时数据的反应是一样的。

为什么把 D 排在最后

网页版评论接口靠请求签名（X-Bogus / a_bogus）鉴权， 签名算法随版本变化。绕它的代价是：随时失效、需要维护登录态、触发风控验证、 以及一个更根本的问题——它没有获得许可。

只读自己的公开评论，性质比写操作轻得多，用于自用观察是可以理解的。 但把它当作产品的地基，等于把稳定性押在一个随时会变、且明确不欢迎你的接口上。 这一条写在这里是为了说清楚边界，不是推荐路径。

现在就能跑的三条命令。 不联网、不需要任何账号、不需要审核。
# 1. 回放完整链路，本地文件接收 python demo_run.py --reasons # 2. 投到企业微信群（把 URL 换成你自己的机器人地址） python demo_run.py --webhook https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxx # 3. 投到飞书 python demo_run.py --webhook https://open.feishu.cn/open-apis/bot/v2/hook/xxx --style feishu

实测输出：11 条评论 → 6 条投递成功、2 条拦截、3 条沉默、0 条无草稿。 每一条都打印判定依据，能直接指着屏幕解释「为什么这条回、那条不回」。

03

六个阶段，每个都是能独立验收的小闭环

划分原则不是「按功能」，是「按能不能单独跑通并验收」。 每个阶段结束时，你手上应该有一个能演示、能测、能判断好不好的东西， 而不是一堆写了一半的模块。

M0演示闭环

把整条链路跑到「手机能收到」

回放真实评论 → 判定 → 生成 → 投递到群机器人。这一阶段不碰任何平台接口， 目的是先把「产品该长什么样」定下来，而不是先解决接入。

验收 11 条评论跑完，四类结局齐全；群机器人收到 6 条消息；屏幕上的判定理由能逐条解释。
已完成 无外部依赖
M1判定校准

用真实评论量出「该回 / 不该回」的准确率

从自己账号导出 100 条真实评论（手工导出即可，不需要接口）， 人工标一遍「这条我该不该回」，跑判定，算一致率。 这一步产出的不是功能，是一个数字——它决定后面要不要继续投。

验收 100 条样本上，判定与人工标注一致率 ≥ 80%。 达不到就调语料和权重，调到达标为止，不要往下走。
需真实评论 门槛：一致率 80%
M2生成质量

让草稿达到「愿意直接发」的水平

接真实模型、补多轮上下文、做话术去重。判定对了但话不像人说， 前面所有工作都白做。这一阶段的主要工作不是写代码，是养语料。

验收 随便抽 20 条草稿，其中至少 12 条你会原样发出去（不改措辞）。 达不到就继续补语料，不要开自动。
需模型 API 门槛：采纳率 60%
M3真实接入

换上真接口，先只读一周

补 OAuth 落地页、回调域名、作品自动发现。接口换真之后， 第一周只拉评论、只出草稿、不发送。这一步用来暴露「假数据永远暴露不了的问题」： 翻页、限流、重复推送、二级评论。

验收 连续 7 天无人工干预，不漏评论、不重复处理、不自回自答； 失败时有告警，不是安静停摆。
需平台审核 门槛：7 天稳定
M4分级放权

让系统自己挣发送权

M1 到 M3 都过了，才轮到打开自动发送。从低风险话术开始， 每小时上限 5 条，每一次人工驳回都扣额度。价格、承诺、售后永远人工。

验收 自动发送占比稳步上升，同时驳回率不上升。 驳回率一旦抬头，立刻退回全人工。
前置：M1–M3 全部达标
M5规模化

第二个账号、第二个平台

多账号隔离、私信能力、数据看板、审计留痕。 判据很简单：接第二个账号时，核心代码改了几行。改得越多，说明前面的抽象没做对。

验收 新增一个账号只改配置，不改 gateway.py。
需企业号（私信）
04

顺序不能换的原因

这条路线有一个明确的先后逻辑：先证明判断对，再证明话说得好，最后才给发送权。 反过来做——先接接口、先开自动——会出现一种很难排查的状态： 系统每天在发消息，但没人知道其中多少条是错的，因为没有人再逐条看了。

M1 和 M2 是整条路线里最容易被跳过、也最不该跳过的两步。 它们没有「接上了」的快感，产出物只是两个数字（一致率 80%、采纳率 60%）。 但正是这两个数字决定了后面要不要继续投人力和钱。 跳过它们直接进 M3，等于用一个还没校准的系统去消耗真实用户。

M0 之所以放在最前面，是因为它最便宜：不需要审核、不需要模型、不需要服务器。 一个下午就能看到完整效果，也就能最早发现「这个产品形态是不是我想要的」。

05

「尽可能回复」这条语义落在哪

需求从「被 @ 就自动回」改成「评论区提到我的人尽量回」，这不只是措辞变化， 判定层的实现跟着变了。

原来的写法是被提及时直接返回满分，等于强制回复。那意味着「@我 6」也会发出去—— 在公开评论区，这比不回更像机器人。

现在改成高权重加分（+0.65）并豁免两项扣分（未被点名、刚回复过）， 结果是被点名且说了事的一律回，被点名但没内容的不回：

评论分数结局
@我 这个多少钱1.00回复
@我 承重多少1.00回复
@我 求链接1.00回复
@我 能便宜点吗1.00拦截（议价）
@我 好看0.65回复
@我 贵0.45观望
@我 6 ／ @我 嗯0.00沉默

注意第四行：被点名要报价，判定说「回」，但风控层先拦下来。 两个层管的是不同的事——判定管「该不该开口」，风控管「能不能说这句」。 合并成一层，就会出现「因为怕报价，所以连问价都不回」。

第六行是「尽量」这个词的全部含义：一个字的「贵」能跨过起始分但不够成一句话， 于是停在观望而不是硬凑一句。第七行的「6」「嗯」连观望都不用，直接沉默。

顺带修掉的一个缺陷

necessity.py 里有一处用了 _lcs_len 却没导入， 只要传入「最近几条消息」的上下文就会 NameError。 现有调用方都没传这个参数，所以它一直没暴露——这类问题在接入真实数据、 开始用上下文的第一个星期就会出现。
