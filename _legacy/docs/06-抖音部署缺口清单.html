01

先纠正一个前提：「被 @」没有接口

抖音开放平台的互动管理只有四个动作，全部以 item_id 为入口。 没有「@我的」消息流，没有 webhook 推送，也没有独立的通知接口。

做得到
  • 评论区里 @ 了你的人 —— 遍历自己作品的评论，用文本匹配昵称
  • 在你回复下面追问的人 —— 拉二级评论列表
  • 同一批新评论按时间排序处理
  • 只回自己发布的视频下的评论（接口强制限制）
做不到
  • 发布视频时 @ 了你的人 —— 那是「提及」，不是评论，无接口
  • 点赞、收藏、关注的通知 —— 不在开放能力里
  • 实时推送 —— 平台不提供 webhook，只能轮询
  • 别人视频下提到你的评论 —— 接口只能按自己的 item_id 查

所以「被 @ 时自动回复」这个需求，准确的表述应该是： 「评论区里 @ 我的人，在下一轮轮询时被发现并回复」。 它不是实时通知驱动的，是轮询 + 文本匹配驱动的，这决定了三件事：

一、有延迟。最坏等于一个轮询周期。建议 3 分钟，再短就是拿接口配额换几秒。 二、会漏。昵称改了、重名了、或者用户把 @ 写成「小陆 你看这个」，都匹配不上。 三、覆盖不全。发布时 @ 你的那批人，这条链路永远接不到，只能靠人工看通知。

这一条比任何功能都重要。 如果产品需求里写的是「用户 @ 我就自动回」，那么这个需求在抖音上不完全成立， 需要改成「评论区提到我的人，我尽量回」。定义差一个词，交付时的落差就是信任问题。

还有一条硬上限，很多人做到一半才发现

/video/list/ 最多 4 页、每页 20 条，合计 80 条作品。 超过 80 条的作品，其评论永远拉不到——这是接口限制，不是实现问题。 代码里已经把这个上限夹死，并标记 truncated， 超出时保留最新 80 条（新视频才有转化价值）。

02

本轮已经补掉的六项

这六项都属于「不补就跑不起来，而且不报错」的类型。 每一条都有测试锁住，108 项全绿。

作品自动发现已补

原来 item_ids 是手写死的，每发一条视频要有人改代码。现在按 /video/list/ 全量拉取 + 差集比较，新增作品自动纳入、删除作品自动移出。

tests: 发现 / 新增 / 移除 / 80 条截断 / 缓存落盘
自回自答过滤已补

自己发的回复也会出现在评论列表里。不过滤就是自己回自己，能无限循环，而且日志看起来一切正常。用「自己的 user id + 发送记录」双保险。

tests: 按 uid 过滤 / 按记录过滤 / 发送后记住
二级评论已补

原来只拉顶级评论。用户在你回复下面追问「看不到啊」，系统完全收不到——而这批人恰恰是意向最强的。现在按 reply_comment_total 变化触发重扫。

tests: 追问入库 / 总数不变不重扫
@ 识别已补

原来 is_mentioned 在 Hub 里写死成 False，等于这个字段从来没生效过。现在做文本匹配，支持昵称截断，并刻意跳过单字昵称防误判。

tests: 常规 / 截断 / 中间位置 / 单字保护
SQLite 持久化已补

待确认队列、已发送记录、信任额度、去重表全部落库。重启服务后队列还在，运营不会以为处理完了其实一条没发。

实测：4 条队列 + 额度 4 跨进程完整恢复
调度与告警已补

定时轮询、指数退避（封顶 30 分钟）、令牌到期预警、队列积压预警。告警按 code 去重，同一个问题一小时只喊一次。

tests: 退避封顶 / 成功重置 / 告警去重 / 令牌天数
顺带修掉一个一直没人发现的缺陷：发送失败被当成已发出。 原来的 approve() 不看 send() 的返回值，接口报错时草稿照样被移出队列。 结果是「日志显示已发送、用户没收到、运营以为处理完了」。 现在失败会退回队列，并保留在控制台里可见。
03

还缺的 12 项

按「上线阻塞 → 一个月内暴露 → 规模化才有用」三档排。 P0 不补，系统能跑但不敢给人用；P1 不补，用一周就会开始出无法解释的问题。

缺口档位外部依赖
01 OAuth 授权落地页现在 token 是 set_token() 手工塞进去的。需要「生成授权链接 → 用户扫码 → 回调收 code → 换 token」这条完整入口，否则换个人用就得改代码。 P0 应用审核通过
02 回调域名与备案OAuth 必须配固定回调地址。国内服务器域名要备案，否则回调无法生效——这一项通常比写代码耗时更长。 P0 域名 + ICP 备案
03 后台鉴权控制台现在无登录、无会话、无 CSRF 防护，只绑 127.0.0.1。一旦放到公网，等于把账号的评论权限公开。 P0 无
04 部署与进程守护没有 Dockerfile、没有 systemd 单元、没有日志轮转、没有健康探针。现在的形态是「开个终端窗口」，关掉就停。 P0 服务器
05 LLM 接入现在是语料检索降级引擎，只能答「见过的问法」。覆盖率上不去，长尾问题一律进人工队列。需要 provider 抽象 + 提示词组装 + 超时兜底。 P1 模型 API key
06 多轮上下文与话术去重用户追问时系统不知道上一条回了什么；同一条视频下连续回复会重复用同一句。这两个问题在第三天就会被用户指出来。 P1 无
07 发送重试与死信队列失败现在只是退回队列，没有退避重试、没有次数上限。接口持续报错时，同一批草稿会在队列里反复堆积。 P1 无
08 语料管理界面改语料要手改 persona.json 再点重置。这是运营每天都要做的事，不该要求会编辑 JSON。还需要覆盖率统计，告诉你哪类问题没被覆盖。 P1 无
09 多账号隔离单 open_id、单 token 文件、单数据库。要接第二个账号时，现在需要复制一整套目录。 P1 无
10 私信能力评论区的转化终点是私信。开放平台有 im 能力（接收及回复私信），但标的是企业号。没有它，获客闭环断在「评论区说一句，然后呢」。 P2 企业号 + im 权限
11 数据看板采纳率、自动率、拦截率、平均响应时长的趋势。没有趋势就无法判断「这周改动到底有没有让回复变好」。 P2 无
12 审计留痕每条回复要能回答「谁发的、依据什么、什么时候」。现在 traces 只在内存，重启即丢。对外提供服务时这是硬要求。 P2 无
04

资质这一关，比我上轮说的乐观

上一轮我给的是「个人主体过不了」。重新查了能力页，需要修正—— 但修正里有一个关键的不确定性，必须同时说。

「视频评论管理」能力页的原话是：「准入条件：暂无准入条件，任一应用均可申请」， 支持的应用类型包括小程序、移动应用、网站应用，审核 2–3 个工作日。 这与我上轮说的「必须有企业资质」不一致。

但社区里的实践反馈是另一回事：多个开发者报告个人主体申请被拒， 理由是「评论管理需要企业或站点资质」，于是转向无头浏览器方案。 两种说法并存，说明真正的卡点可能不在「能力」本身，而在你能创建什么类型的应用—— 个人通常只能开小程序，而网站/移动应用往往要求企业主体。

所以现实的路径是：个人小程序 → 申请评论管理能力 → 等审核。 这条路的成本最低，也最可能通过。不要先去注册公司。 申请时用途写「统一查阅并回复自己账号下的评论，做客服答疑」， 不要写「营销获客」——后者会被按营销工具处理，而那个方向是收紧的。 以控制台实际显示的结果为准，任何人的经验都可能过期。

按这个路径，时间线大概是这样

  • 注册小程序主体，创建应用拿到 client_key / client_secret半天 · 现在就能做
  • 申请「视频评论管理」能力填写真实使用场景，等待审核2–3 个工作日
  • 补 OAuth 回调 + 后台鉴权 + 部署也就是上面的 P0 四项3–5 天
  • 先跑只读模式只拉评论、只生成草稿、不发送，验证判定是否可信1–2 周
  • 打开分级放权从低风险话术开始，观察采纳率持续

值得注意的是：在等审核的这段时间，代码可以全部写完并测完。 因为网络层是可注入的——假数据跑通的逻辑，换真 transport 就直接生效，中间没有需要重写的部分。

05

上线前的检查清单

左边是要做的事，右边是责任方。凡是标「你」的，都不是技术问题，是账号与资质问题。

  • 应用创建完成，拿到 client_key / client_secret你
  • 「视频评论管理」能力审核通过你
  • 「查询授权账号视频列表」权限通过（否则作品发现不可用）你
  • 回调域名可用且已备案你
  • OAuth 授权页可完成「扫码 → 回调 → 换 token」代码
  • 后台登录鉴权就绪，未授权请求一律拒绝代码
  • 服务以守护进程运行，崩溃自动重启代码
  • 告警能发到你的手机（企业微信 / 钉钉 / 短信）代码
  • 只读模式跑满一周，草稿采纳率 ≥ 60%你来判断
  • 分级放权开启，且小时上限 ≤ 5 条代码
  • 准备好随时一键关停（autopilot=False）代码
最后一条不是形式主义。自动回复这类系统出问题时，最贵的不是修 bug 的时间， 而是它在你发现之前连续发了多少条。所以「能一键停」必须在上线前就验证过一次， 而不是等到需要的时候才去找开关。
