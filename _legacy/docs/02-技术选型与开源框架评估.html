Framework Selection

平台内能扒
平台外更能扒

换了这个问法之后，答案比上一轮乐观得多。你要的两件事其实是两个产品： 平台内的文字自动回复，和平台外的 AI 陪伴应用。 前者有一整套成熟的社区协议和框架可以扒，后者有一个 MIT 许可、四万四千星的项目几乎现成。 真正需要你自己判断的，是许可证和「双端」这两个坑。

平台内 · 文字回复 能实现

QQ 有 OneBot 事实标准；抖音有官方评论回复 API；微信只剩 PC hook 一条路，且底座已停更。

平台外 · 陪伴应用 能实现

AIRI（MIT）已把语音、Live2D、陪玩 Minecraft 做完，可直接当底座改。

双端 · 电脑 + 手机 换架构才行

手机端去接管微信物理上做不到。正解是执行端放服务器，手机只当遥控器。

01

先把需求拆成两个产品

reframe

你说「如果不在平台，那就需要有更多功能，比如语音、陪伴聊天、打游戏」。这句话其实揭示了一个关键分岔： 这两个方向的技术栈、许可证、上架路径完全不同，不能塞进同一个 APP 里。 硬要合并，结果是两头都做不好——一边被平台封号，一边功能半成品。

Product A

平台内 · 文字回复中台

跑在服务器或 PC 上，接多个平台的消息流，用统一人设生成回复，按风控规则发送。

  • 用户是「你自己」——替你把消息回掉
  • 手机端是遥控器，不是执行端
  • 核心难点在协议与风控，不在 AI
  • 不建议上架应用商店
Product B

平台外 · AI 陪伴应用

你自己的聊天产品。有形象、有声音、有记忆，可以陪你说话、陪你玩。

  • 用户是「你的用户」——你提供产品
  • 双端天然成立，iOS 安卓都能上
  • 核心难点在语音延迟与人格一致性
  • 可以正经收费、正经上架
取舍建议：把 A 当成你的运营工具（不上架、自用），把 B 当成你的产品（上架、收费）。 两者共用同一份「人设中枢」，这正好接上你上一轮问的人设统一窗口——那套设计在这里是通用的。
02

03

「电脑和手机都能用」的真实解法

architecture

这句话有一个隐藏前提需要先破掉：如果你理解成「手机也能去接管微信」，那 iOS 端物理上做不到—— 系统不允许一个 App 读取并操作另一个 App 的界面。安卓靠无障碍服务勉强可以，但也违反微信规则。

正确的解法是把执行端和控制端拆开。执行端跑在服务器或常年开机的 PC 上，负责连平台； 控制端是手机 APP / 网页 / 桌面客户端，只负责看和指挥。这样「双端」才真正成立， 而且顺带解决了另一个问题：你不需要让手机 24 小时亮屏挂着。

控制端（手机/网页/桌面）↔ 你的网关 ↔ Hub（人设·闸门·引擎）↔ 适配器 ↔ 平台。 所有平台协议都止步于适配器层，控制端永远不需要知道对面是 QQ 还是抖音。

05

许可证：比技术难度更值得先看

license risk

这是「扒代码」这件事上最容易踩的地方。技术能不能跑通，试一天就知道； 许可证选错，等到要收费、要融资、要被收购的时候才发现，代价是重写。

绿灯

MIT / Apache-2.0 —— 可以闭源商用

AIRI、Open-LLM-VTuber、NoneBot2 都是 MIT。你可以改完闭源发布、可以收费、不必开源你的修改。 唯一义务是保留版权声明。

黄灯

AGPL-3.0 —— 能用，但有传染性

AstrBot 是 AGPL-3.0。它的特点是网络使用也算分发：只要用户通过网络使用你修改过的版本， 你就必须把修改后的完整源码按 AGPL 提供给他们。
三种应对：① 完全不改核心，把它当独立进程，你自己写网关调用它（法律上更接近「聚合」）； ② 接受开源，靠服务而非代码收费；③ 换成 MIT 的 NoneBot2 自己搭。

红灯

已归档项目 —— 不是法律问题，是工程问题

WeChatFerry 已归档、go-cqhttp 已停更。它们锁死在特定微信版本上，微信一升级就失效。 拿来读源码、理解协议可以；拿来当底座，等于把一个有明确失效日期的技术依赖写进架构， 而这个日期不由你决定。

还有一个隐藏的许可问题：Live2D 模型文件本身受 Live2D Inc. 的授权条款约束， 开源项目的 MIT 只覆盖代码，不覆盖你用的模型资产。要商用就得单独确认模型授权，或改用 VRM。
06

三套可直接落地的组合

recommendation
A

运营工具：AstrBot 或 NoneBot2 + NapCat 先做这个

不自研底层。用 NapCat 解决 QQ 连接，用 AstrBot 解决多平台适配与人格管理， 你只写「人设 + 风控 + 业务插件」。一周内能看到效果。

选 AstrBot 的前提是接受 AGPL（或者你只调它的 API 不改核心）；要闭源就换 NoneBot2 自己搭一层。

周期 · 1–2 周 许可 · 注意 AGPL 上架 · 不需要
B

陪伴产品：AIRI 当底座 + 自研移动端外壳 上限最高

AIRI 是 MIT，可以直接改。它已经把最难的三件事做完：实时语音闭环、Live2D/VRM 驱动、 在 Minecraft / Factorio 里真正操作游戏。你要做的是把移动端体验补齐、把人设中文化、 把付费和账号体系做出来。

注意：官方只支持 Web / macOS / Windows，没有移动端，README 里也没有任何 Android / iOS 说明。 手机端最省力的路径是把它的 Web 版做成 PWA，或者包一层 Capacitor 外壳—— 代码里有 Capacitor 痕迹但没作为正式能力发布，等于你要自己补完这一段。

周期 · 2–4 个月 许可 · MIT 可闭源 上架 · 需自补移动壳
C

混合形态：A 做工具，B 做产品，共用人设

同一个「人设中枢」同时喂给两套系统：A 用它回别人的消息，B 用它陪你的用户聊天。 人设只维护一份，改一处两边同步生效——这正是你上一轮问的那个人设窗口的真正价值。

07

已经写好并跑通的最小骨架

app/gateway/

与其继续讨论架构，我直接把骨架写出来跑了一遍。它不依赖任何第三方包， 三个核心路径都有用例覆盖：边界拦截、自动发送、人工审批。

# python gateway.py demo —— 实际运行输出 人设：小陆｜示范语料 12 条｜知识 4 条｜边界 9 条 [已发送] qq/阿哲 → 承重 30 公斤，桌面放个卡式炉完全没问题。 [已发送] qq/阿哲 → 搬得动，2.4 公斤，单手就能拎走，收起来跟伞差不多长。 [拦截] qq/阿哲：命中人设边界：便宜 [已发送] wechat/米粒 → 在的，你说。 [已发送] wechat/米粒 → 今天下单后天到，我这边盯着发货。 [已发送] xhs/用户8823 → 链接在主页置顶，或者我私发你。 [拦截] wechat/米粒：命中人设边界：退款 -------------------------------------------------------------------- 审批链路：入队 1 条｜放行 成功｜放行后发送 1 条 自检：边界拦截 ✓｜自动发送 ✓｜人工审批 ✓ 结果：全部通过

加一个渠道要写多少代码

两个方法。适配器只做「收」和「发」，人设、风控、生成逻辑全都不用碰：

class DouyinAdapter(ChannelAdapter): name = "douyin" auto_send_allowed = False # 官方通道，先人工确认 def poll(self) -> list[Inbound]: # 调 /video/comment/list/ 拿新评论，转成 Inbound ... def send(self, reply: Reply) -> bool: # 调 /video/comment/reply/ 发回复 ... # 注册，核心一行不用改 hub.register(DouyinAdapter(...), channels=["douyin"])

写的过程中发现并修掉的两个真问题

第一个：草稿被静默丢弃。 第一版里 Hub 用「适配器名」当字典键。跑 demo 时自动发送全过、拦截全过，看起来是绿的—— 但待确认队列永远是 0，说明人工审批那条路径根本没被执行到。 补了用例才暴露：模拟适配器名叫 mock，消息渠道是 wechat， 审批时按渠道查不到适配器，草稿被 pop 掉又没发出去，全程没有任何报错。 改成「适配器列表 + 渠道到适配器的映射」分开维护后才修好。

第二个：中文关键词匹配漏判。 人设里写的边界词是「打折」，用户实际说的是「给我打个折」——字面带不上，直接放行。 15 个单元测试里这一条是红的，我才发现。 修法是允许关键词各字之间最多隔 2 个字（打.{0,2}折 就能命中）， 同时加了一个反向用例「我今天打了电话」确保不会过度拦截。

这两个问题都有一个共同点：不报错，只是悄悄做错事。 所以骨架阶段就把单测写好，比等到业务代码里才发现便宜得多。

# python -m unittest test_gateway -v Ran 15 tests in 0.002s OK # 覆盖：风控纯函数 6 项 · OneBot 事件归一化 4 项 · Hub 路由 4 项 # 其中 2 项是上面两个真实缺陷的回归锁

四句话收尾

  1. 平台内的文字回复能实现，但微信是第一个绕不过去的障碍。 QQ 有 OneBot 这套事实标准，NapCat 能无头跑在 Linux 上；抖音有官方评论回复 API（要企业资质）； 小红书只能浏览器自动化。微信个人号只剩 WeChatFerry，而它 2025 年 5 月已经归档停更。
  2. 「手机也能用」要靠架构换，不靠技术硬啃。 执行端放服务器、控制端放手机，双端才成立。想让手机本地去接管微信，iOS 上不存在这条路。
  3. 陪伴应用这条路更值得投，因为许可证对。 AIRI 是 MIT，四万四千星，语音、Live2D、陪玩 Minecraft 都做完了，可以直接改。 AstrBot 覆盖平台最多但是 AGPL，改了要开源——这决定你能不能用它做闭源生意。
  4. 底层别自己造，但适配器必须自己写。 协议端、消息总线、语音管线都用现成的；把「人设 + 风控 + 适配器」这三样握在手里， 这是唯一形成差异、也唯一出事时你能看懂日志的地方。
