Surface-aware Routing

同一套骨架，
三套参数

你的判断对了一半：抖音、小红书评论回复和 QQ、微信自动回复 确实是同一条流水线，Hub 一行都不用改。 但「同一条流水线」不等于「同一套参数」——评论和私信在 五个地方必须区别对待，其中最要紧的是公开性。

相同
五段流水线完全复用

归一化 → 人设 → 风控 → 生成 → 发送。适配器换掉，Hub 不动。

不同
判定阈值与风控等级要分档

评论是公开的，回错一次所有人都看得见。默认强制人工确认。

01

能复用的是哪五段

把平台差异全部挡在适配器里之后，中间这五段对所有渠道都一样。 这也是为什么加抖音、加小红书不需要动核心代码——只加一个 Adapter。

01归一化Inbound
02人设注入Persona
03风控闸门Guard
04生成Engine
05发送Adapter

五个环节全部复用。唯一新增的是第 02 与 03 之间的一层：回复必要性判定—— 它需要知道消息出现在什么场合，所以 Inbound 多了一个 surface 字段。

02

必须区别对待的五处

维度 私信 / 群聊 评论 改在哪
会话模型thread 线性对话，一条接一条 树状：笔记/视频 → 一级评论 → 楼中楼 Inbound 加 thread，存 note_id / item_id。回复必须挂在这下面，否则变成新的顶级评论
触发语义intent 消息一定是冲你来的 大部分在评价内容，不一定是找你 评论场景新增购买意图词（求链接 / 在哪买 / 怎么买），命中才接；纯夸赞不接
公开性publicness 一对一或小群，回错影响小 所有人可见，回错是公开事故 评论默认 强制人工确认，要全自动必须显式打开 allow_public_auto
频率rate 一分钟回几条正常 高频回复是刷评特征 评论场景「刚回复过」的惩罚同样生效，且平台侧还有 QPS 限制
通道能力transport OneBot / 官方 API 都能收发 抖音有 API，小红书没有 两个适配器行为完全不同：一个真发，一个只出草稿。上层无感知

前四条是逻辑差异，最后一条是能力差异。逻辑差异决定了阈值要调， 能力差异决定了有些平台只能半自动——两者不能混为一谈。

03

同一条消息，三种场合，三种结局

下面三条都是「求链接」——文案一样，但因为出现场合不同，系统给出的判断不同。 这就是 surface 这个字段存在的全部理由。

私信 private
语料相近 100%+0.25
一对一必答+0.40
合计0.65
回复　→　可自动发送
群聊 group
语料相近 100%+0.25
强相关豁免扣分±0
合计0.25
沉默　→　不是冲你来的就不接
评论 comment
购买意图+0.50
语料相近 100%+0.25
合计0.75
回复　→　默认进人工队列

以上是实测值，不是估算：judge(Inbound("x","1","u","求链接",surface=...)) 跑出来的。 注意群聊那一列——同样是「求链接」，群聊里会被判沉默。因为它没 @ 你， 在一群人中间突然插一句卖货，比不回更像机器人。
还要注意评论那一列：分数够，但默认仍然不自动发出去。 同一个工具在私信里出错是小事，在公开评论区出错是所有人都看得见的事。

实测输出

# python adapters.py —— 四条评论，四种结局 [待确认] xhs/用户A → 链接在主页置顶，或者我私发你。 [沉默] xhs/用户B 分数 0.0：公开评论区且无明确购买意图 -0.10 [待确认] xhs/用户C → 链接在主页置顶，也可以私信我发你。 [拦截] xhs/用户D：命中人设边界：便宜 待确认 2 条｜沉默 1 条｜拦截 1 条

用户 A 说「求链接」、C 说「这个在哪买」→ 生成草稿。 B 说「这个好看」→ 不接，因为夸赞不是购买意图，接了反而像营销号。 D 说「能便宜点吗」→ 边界拦截，不报价。

04

同为评论，两个平台的通道完全不同

这是最容易被忽略的一点：抖音和小红书看起来都是「评论回复」， 但在代码里它们的实现方式毫无共同之处。

抖音官方通道能真发
  • GET /video/comment/list/ 拉评论
  • POST /video/comment/reply/ 回复
  • 需企业主体 + 应用转正 + 互动管理权限
  • 回复内容上限 500 字，有 QPS 限制
能拿到结构化的 comment_id，回复能精确挂到某条评论下。 代价是资质门槛——个人主体基本过不了审核。
小红书无公开接口只能出草稿
  • 没有面向第三方应用的评论读写接口
  • 社区方案都是浏览器自动化，依赖登录态
  • 页面结构一变就失效，风控随时可能打断
  • 回复里带站外联系方式几乎必封
这里的适配器不假装有接口：它把生成的草稿写进 outbox， 由你复制粘贴发布。链路依然是通的，只是最后一步由人完成。

这个设计的价值在于：即使一个平台完全没有接口，产品逻辑也不会因此断裂。 读意图 → 生成 → 审核 → 发布，四步都在，只有最后一步从「自动」变成「手动」。 这比为了自动化去写一套随时会坏的浏览器脚本要稳得多。

05

跑的时候抓到一个答非所问

用户问「这个在哪买」，回复了「承重 30 公斤」

第一版用 LCS 的绝对值做语料匹配，阈值是 2。中文里「这个」两个字就够 2 分， 于是 这个在哪买 匹配到了 这个桌子承重多少， 返回了承重参数。

这比不回复更糟——不回复只是错过一单，答非所问会被一眼认出是机器人。 而且这个缺陷不会报错，测试也全绿，只有把整条链路跑起来看输出才会发现。

修法是把绝对长度换成覆盖率：LCS 长度除以较短那条的长度。 「这个在哪买」和「这个桌子承重多少」覆盖只有 33%，不匹配； 「求链接」和「求链接」覆盖 100%，命中。

# textutil.coverage —— 归一化之后的相似度 def coverage(a, b): m = min(len(a), len(b)) return lcs_len(a, b) / m if m else 0.0 # 3 字以内的语料（"在吗"）必须精确命中，否则会被大量长句抢走 if len(q) <= 3 and cov < 0.99: continue

另外补了一句产品侧的动作：人设语料里原本没有「这个在哪买」这类问法， 所以即使匹配修好了也答不上来。加了三条购买意图语料之后，评论链路才真正通顺。 改阈值只能止损，补语料才是提升。

同一轮还抓到第二个：私信里「求链接」被判观望

加完 surface 之后重算三档，发现私信场景只拿到 0.55——卡在 0.60 阈值下方， 被判成观望。一对一说「求链接」是你能拿到的最强购买信号， 系统却选择不吭声。这种漏答比答错更难发现，因为日志里只多了一行「沉默」。

修法是把私聊基础分从 0.30 提到 0.40。这个数值不是拍的—— 是按「最短的有效语料（3 个字）+ 最低必要信号」反推出来的： 0.25 的语料分加上 0.40 必须过 0.60。

两个缺陷都补了回归测试。现在 35 项测试覆盖：风控纯函数、OneBot 事件归一化、 Hub 审批队列、三档必要性判定、评论意图识别、引擎匹配防答非所问。

四句话

  1. 是同一套逻辑，但要加一个维度。 五段流水线完全复用，新增的只有 Inbound 上的 surface 字段—— 它告诉判定层"这条消息出现在什么场合"。
  2. 评论和私信最大的差别不是格式，是公开性。 私信回错影响一个人，评论回错所有人都看得见。所以评论默认强制人工确认， 要全自动必须显式打开，这个默认值不该改。
  3. 评论要克制，只接购买意图。 夸赞、闲聊、表情都不接。评论区的价值是筛出想买的人， 不是把每条评论都回一遍——后者反而像营销号。
  4. 抖音能真发，小红书只能出草稿，这个差异挡在适配器里。 Hub 不需要知道对面有没有接口。没有接口时降级为人工粘贴， 链路依然完整，只是最后一步从自动变成手动。
