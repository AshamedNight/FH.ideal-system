Channel / 微信还是抖音

微信更快，但先接受一个前提

「微信自动回复」这句话落到实处是企业微信，不是个人微信。 个人号那条路腾讯已经明确列为外挂，封号是阶梯式的，不是概率问题。 企业微信是官方接口，不需要应用审核，注册个主体就能建应用—— 所以它确实比抖音快，代价是要写一套加解密。

01

五条路的真实差距

「快」要分两层看：多久能拿到资格，多久能写出可用的东西。 有的渠道资格当天就有，但代码要写三天；有的反过来。

渠道官方支持资质 开发量封号风险拿到资格
企业微信自建应用 是 企业或个体户 2–3 天 低 当天
微信公众号客服 是 认证服务号 2–3 天 低 认证 1–2 周
QQ + NapCat 否 无 1 天 中 当天
抖音评论回复 是 应用审核 已完成 低 2–3 工作日
微信个人号 明确禁止 — 1–2 天 极高 —
个人微信为什么不做。 腾讯安全中心的外挂打击公告把「微信机器人：定时群发、自动回复、自动聊天」直接列在名单里。 这类工具锁死特定微信版本，微信一升级就失效，而且封的是登录账号本身—— 号里面的联系人、群、聊天记录一起没了。这不是技术方案的问题，是账号资产的问题。
02

现有代码能不能直接用

不能直接跑，但改的是外壳，不是内核。这也是这次拆解想要的结果： 加一个渠道 = 加一个适配器。

模块企业微信要不要改说明
gateway.py（Hub） 0 行 注册渠道时传 channels=["wecom"] 就行
necessity.py（判定） 0 行 判定只看文本和意图，不看渠道
autopilot.py（放权） 0 行 话术风险和额度与渠道无关
store.py（持久化） 0 行 队列表本来就按渠道分列
persona_schema.py 换配置 微信聊天和评论区语态不同，语料要重写
新增 wecom_crypto.py 新写 AES-256-CBC 加解密 + 签名，约 250 行
新增 wecom.py 新写 客户端 + 适配器，约 200 行
新增 wecom_server.py 新写 回调服务，约 280 行

这三个新文件已经写完了，并且用两组公开测试向量验证过： FIPS-197 的 AES-256 向量，以及企业微信文档里那份带密文和签名的完整样例。 签名算出来是 477715d1…f3e6，解密出的明文和文档展示的一致。

加解密的正确性不是靠"看起来能跑"判断的。 AES 实现错一位，往往表现为「大部分消息能解、偶尔解出乱码」， 排查时根本不知道错在哪。用官方向量对齐，是唯一能一次确认的办法。

跑起来长什么样

# 1. 复制配置模板，填四个值（都在应用详情页） cp wecom.example.json wecom.json # 2. 先只收不回，确认回调通 python wecom_server.py --config wecom.json --dry # 3. 关掉 --dry，按闸门决定是否回复 python wecom_server.py --config wecom.json

服务会打印回调地址，填进「应用管理 → 接收消息 → 设置API接收」， 填的时候企业微信会立刻发一次验证请求——通过就说明加解密没问题。

03

「抖音只做评论回复」能省多少工作量

省不了多少，因为你现在做的就是最小范围。 上传图片、生成文案、自动发布那一大块，从第一轮就否掉了——不是没做，是不该做。

把项目按工作量拆开看：

部分占比换渠道要不要重做
判定 + 生成 + 风控 + 放权 约 70% 不重做，但需要重新校准（M1/M2）
语料与人设 持续投入 每个账号都要重写
渠道接入 约 15% 每个渠道写一个适配器
运维（部署/告警/持久化） 约 15% 不重做，一套通用

接入只占 15%，而其中抖音那一半已经做完了。所以「缩小范围」这个动作， 能砍掉的空间很小——真正的成本在「判定准不准、话像不像人」， 那部分和渠道无关，也和范围无关。

一个容易算错的账： 「只做评论回复」听起来像砍掉了一半功能，实际上从第一轮起项目就只有这一半。 现在的瓶颈是 M1（一致率 80%）和 M2（采纳率 60%）， 两个都是质量指标，不是功能数量。多做一个渠道不会让它们变好， 少做一个功能也不会让它们变简单。
04

所以下一步按这个顺序

  1. 企业微信跑通真实收发 它是唯一「不需要等审核、官方支持、能拿到真实对话数据」的渠道。 跑通之后，M1 的一致率可以用真实聊天来测，而不是靠假数据回放。 3–5 天 · 需要个体户或企业主体 · 需要一个公网可访问的地址
  2. 同时申请抖音评论权限 个人小程序提交，用途写「统一查阅并回复自己账号下的评论」。审核 2–3 个工作日， 这段时间正好用来做第 1 步。 提交 1 天 · 等待 2–3 工作日
  3. 权限下来后，抖音只换适配器 判定、生成、放权、持久化全部复用。需要补的是 OAuth 落地页和回调域名—— 这也是之前列的 P0 四项里的两项。 3–5 天 · 主要是备案和部署
  4. 然后才是 M1 校准 拿到真实数据后跑一致率，达不到 80% 就调语料。 这一步之前不该开自动发送。 1–2 周 · 主要时间花在标注上

把企业微信放在第一位，理由不是它更简单，是它能最快拿到真实数据。 现在的判定只用 11 条构造的评论验证过，真实分布的差距还没暴露—— 越早接触真实消息，越早发现判定偏到哪里。

05

企业微信有三个限制要先知道

限制影响怎么解
只能发给内部成员 自建应用的消息对象是企业成员，不是外部客户。用于「同事之间」或「自己两个号对聊」没问题 要触达外部客户，需要开通「微信客服」或「客户联系」，那是另一套接口和权限
回调必须公网可达 本机 127.0.0.1 收不到平台推送 反代（Nginx）+ 域名，或内网穿透。本地调试可以先穿透，正式跑要备案域名
5 秒响应窗口 判定 + 生成超过 5 秒就超时，平台会重试三次 回调只做验签解密入队、立刻返回空串；回复走主动发送，不受窗口限制

第一条最容易被忽略。如果你要的是「给外面的人自动回复」， 企业微信自建应用做不到，得走微信客服——那是另一套东西，成本更高。 如果只是「验证自动回复能不能跑通」，内部应用完全够用，而且当天就能开始。

建议先用两个号对聊验证。 一个号当客服、一个号当顾客，整个流程（收消息 → 判定 → 生成 → 回复） 和真实场景完全一样，只是对象是自己。这一步不需要外部客户， 也不需要「微信客服」权限。
