NEXUS 技术档案 No. 03 · 无障碍与平台边界 核查于 2026-11-09
Android Accessibility · Platform Boundary

跳过接口
能拿到什么，
又会暴露什么

安卓无障碍确实可以绕过所有开放平台，直接读屏、填字、点发送。 但它同时也会被看见——这一点决定了这个方案能走多远。 另外，交友类平台的性质和 QQ 群不一样，需要单独说清楚。

安卓无障碍 能做

无障碍服务可跨应用读节点、填文本、点按钮。iOS 完全没有这条路。

被检测的程度 完全可见

包名在系统服务列表里，行为节奏在日志里。不是"可能被发现"，是"一定可见"。

交友类平台 性质不同

心遇的女性回复可换钱。在这里做自动回复，性质不是违规，是骗取分成。

配套代码 app/android/ 判定逻辑 app/gateway/necessity.py 已跑通 25 项单测
01

技术链路：四步，每步都有坑

read → decide → fill → send

安卓的无障碍服务（AccessibilityService）是系统给视障用户准备的接口， 它能读取当前窗口的完整控件树、取到每个控件的文字、并代替用户执行点击和输入。 这套能力用来做自动回复，技术上没有障碍——难的不是"能不能做"，是"做完之后能不能稳定地用"。

环节用什么实际会卡在哪
读消息 AccessibilityNodeInfo 树遍历 能拿到全部可见文本，但分不清"谁发的"。气泡左右对齐、头像位置各 App 不同，只能靠上下文猜
找输入框 viewId / className / text 各 App 命名不统一，版本升级会变。必须做成可配置的选择器链，写死在代码里撑不过三个版本
填文字 ACTION_SET_TEXT 自绘输入框不响应该动作，只能退回"点击唤起输入法再注入"，稳定性明显下降
点发送 ACTION_CLICK 节点在界面刷新后立即失效。填完字重新取根节点是必须的，缓存旧引用必崩

我在 app/android/ 里写了完整骨架：服务主体、声明式选择器、节点查找与填入。核心设计是把「怎么找界面元素」抽成 JSON， 新增一个 App 只改配置不改代码——否则接第五个 App 时代码就没人敢动了。

// 新增一个 App 的全部工作：写一段配置 "com.example.app": { "input": [{ "by": "className", "value": "android.widget.EditText", "pick": "last" }], "send": [{ "by": "text", "value": "发送" }], "message": [{ "by": "className", "value": "android.widget.TextView" }] }
02

它能看到的你，比你想象的多

what the target app can see

很多方案文档在这里含糊过去，说"只要伪装得好就没事"。这是不负责的。 下面四层每一层都是确定可见的，区别只在于对方有没有专门去看。

①②③ 三层是技术层面直接暴露的，越往上越难规避。④ 与你的技术方案无关， 但决定了平台愿意给你多大的容错空间。任何声称"完全不被检测"的方案，都是在回避这三层里至少一层。

真正能降低命中率的不是"隐藏"，是让行为本身不像机器： 不秒回、有间隔抖动、同一话题不连续轰炸、偶尔答不上来就说"我确认一下"。 这也是为什么我在 PC 端的判定里加了「回复必要性」——真实聊天里最大的破绽不是语气，是每条都回。

一个人对群消息的回复率通常远低于 50%。如果你 100% 都回，那不是像人，那是像客服机器人。 — app/gateway/necessity.py 的设计前提
03

交友平台：这里的问题不是风控

the line that is not about technology

你点名了心遇和他趣。我查了心遇的公开资料，发现一件必须先讲清楚的事： 它的商业模式是谁先发消息谁付费，男性发一条约 0.24–0.43 元， 女性回复可获得金币并提现。这意味着在这个平台上做自动回复，性质会变。

同一个技术，在不同平台上性质完全不同

在 QQ 群里自动回复，违反的是平台用户协议，后果是封号。

在心遇这类「女性回复可提现」的平台自动回复，实际效果是： 用机器冒充真人，让对方按条付费，再从平台把金币提出来。 这已经不是协议问题了——收钱的一方是平台，付费的一方是真人用户， 中间那个"人"是假的。

公开报道里，已经有大量用户怀疑"屏幕另一头是 AI 机器人"，黑猫投诉平台相关投诉超过 1200 条。 这说明平台方自己也在这件事的争议中心，对第三方机器人的打击只会更狠，不会更松。

我把这条线画在这里，不代表替你判断你的用途。如果你的目标是 自己经营一个真实身份、用 AI 帮打字，那是另一回事； 如果是批量养号冒充女性赚金币，那我不会帮你做这个， 技术上也建议你不要碰——它不是"被发现就封号"的成本，是可能被追究的成本。

他趣这类平台的特殊性

他趣是"情趣电商 + 社交"的组合，内容侧涉及成人话题，监管口径比普通社交更严。 自动化引流在这类平台上除了平台风控，还会碰到内容合规的额外审查。 技术上同样能用无障碍做，但可预期的账号生命周期以天计，投入产出不成立。

可行的用法：只做草稿，不代发

我在安卓骨架里把默认值设成了 Mode.autoSend = false： 只把草稿弹在悬浮窗上，点不点发送由人决定。这样：

性质上

最终发送动作由人完成，工具性质是"辅助输入"，不是"代替你社交"。这条界限在平台规则和常识上都更站得住。

效果上

打字这件事本来就占了大半时间。你从"想措辞 + 打字"变成"看一眼 + 点一下"，省下的时间已经很多。

风控上

发送间隔由人控制，不会出现机器特有的固定节奏。这是最有效的降风险手段，比任何伪装都管用。

成本上

不需要为了绕过检测去研究 root、LSPosed、设备指纹伪造。那套东西的维护成本远超收益。

04

AstrBot：决定开源之后，
许可证反而不再是问题

from constraint to advantage

上一轮我把 AGPL-3.0 列为"黄灯"，前提是你要做闭源产品。 既然你决定改完直接开源上 GitHub，这个约束就消失了——AGPL 正好要求下游也开源， 和你想要的结果一致。所以这条路现在是通的，而且是最省力的。

改造应该分三层，不要动核心

层改不改怎么改
平台适配层adapter 改 加安卓无障碍适配器、加抖音评论适配器。这部分本来就是要自己写的，AstrBot 只提供接口形状
插件层plugin 改 业务能力全放插件里：人设注入、风控闸门、线索台账。插件是官方鼓励的扩展方式，改它不污染主干
核心层core 尽量别动 消息总线、事件分发、WebUI。改核心会让后续合并上游更新变成灾难，而 AstrBot 更新很频繁

一个容易被忽略的细节：AstrBot 有自己的 EULA

除开源许可证外，它还有一份最终用户许可协议，其中写明该项目"不构成任何形式的商业服务"。 如果你只是开源代码，不冲突；但如果你打算基于它做付费托管服务，需要单独读一遍 EULA 原文， 不能只看 LICENSE。许可证和 EULA 是两份文件，各管各的。

开源前必须做的一件事

清理历史提交里的密钥。这类项目最容易在 config 或 .env 里留下 API key、OneBot token、数据库密码。推到 GitHub 之后，这些 key 会在几分钟内被扫到并盗用。 建议开仓库前先跑一遍密钥扫描，把历史记录整个重写一遍，而不是在新提交里删掉——旧提交仍然可查。

05

MaiBot 值得借的，
恰恰是它「不说话」的部分

what to borrow, what to skip

我看了它的设计文档和公开的源码结构。它最有价值的不是话术，是四个工程决策—— 而且这四个都能直接搬进你的项目，不需要搬它的代码。

01
心流 / 激活度HeartFlow · reply_necessity
它不是"收到消息就回"，而是给每条消息打激活度分数，超过阈值才开口，大部分时候保持沉默。 三种模式：普通聊天按阈值回、专注聊天每几秒观察一轮、自动模式按群活跃度切换。

这是最该抄的一条。我在 necessity.py 里做了简化实现：问句 +0.35、命中知识 +0.30、 与语料相近 +0.25、私聊 +0.30，群聊未被点名 −0.15、连续发言 −0.25。 跑出来 10 条消息只开口 6 条。
02
记忆分层A_Memorix / LPMM
它把"记忆"拆成四件事，而不是一个向量库：短期上下文窗口（带压缩）、 对话窗口摘要进长期、人物事实抽成画像、回答前检索并注入。

“越来越懂你”靠的是回复之后的写回，不是把聊天记录越塞越长。 少了写回这一步，记忆就只是一段不断变长的日志。
03
表达层与推理层分离style / thinking
"想什么"和"怎么说"是两套逻辑。所以调人格风格时不用动推理链路。

它还刻意做了一些不完美：连发几条碎片消息、大小写不一致、偶尔打错字、按情绪发表情包。 这些在工程上是"降低质量"，在产品上是"提高像人程度"。这个取舍值得抄。
04
关系与黑话relation · slang mining
每个用户、每个群都有独立的关系记录和亲密度分数；还有一套黑话挖掘， 自动检测高频圈内用语并在合适场景用出来。

对你的场景，关系系统比黑话更实用——它能让"同一个人第三次来问"和"陌生人第一次问"得到不同回复。
不该抄的部分也很清楚：MaiBot 的目标是"在群里当个像人的群友"，不是完成任务。 它的官方文档自己也说，这种拟人化的代价是「人格没法像意图分类器那样做单测」。 你要做客服/获客场景，确定性和可审计性比"像人"更重要，别把这一半也抄过来。 — 取舍依据：MaiBot 官方定位与 EULA

已经落地的部分

necessity.py 是可跑的：python gateway.py flow 会打印每条消息的分数、决策和逐条理由。理由是可解释的——线上判定错了，能直接看出是哪条规则生效。

# python gateway.py flow 1. [群] 阿哲：这个桌子承重多少 → 0.85 / 回复 · 含问句特征 +0.35 · 命中知识条目（产品参数）+0.30 · 与示范语料相近（重合 8 字）+0.25 · 群聊但消息强相关，不扣参与欲 5. [群] 路人甲：嗯 → 0.0 / 沉默 · 纯语气词，无信息量 9. [私] 米粒：多久能到 → 1.0 / 回复 · 含问句特征 +0.35 · 命中知识条目（发货）+0.30 · 私聊场景（一对一必答）+0.30

跑的过程中发现两个判定失衡，都改了：一是私聊里「多久能到」被判成观望—— 一对一场景用户已经开口问了，装看不见是失职；二是群里「搬得动吗」因为没被 @ 就掉到观望， 而它明明和语料重合十个字。现在的规则是强相关时豁免"未被点名"的扣分， 并且私聊不吃"刚说过话"的惩罚。这两条都补了回归测试。

06

许可证拼图：
AGPL 和 GPLv3 能不能拼在一起

license compatibility

你的计划是改 AstrBot（AGPL-3.0）并参考 MaiBot（GPL-3.0）。这两个能不能放进同一个仓库？能。

项目许可证放进你的开源仓库时的义务
AstrBot AGPL-3.0 你的整个衍生作品按 AGPL 发布，包括通过网络提供服务时。用户有权拿到完整源码
MaiBot GPL-3.0 AGPL-3.0 明确允许吸收 GPLv3 代码，组合后整体受 AGPL 约束。所以你的仓库发布为 AGPL-3.0 即可，不需要双许可
OneBot 实现NapCat 等 各仓库为准 通常作为独立进程通信，不并入你的代码库，一般按"聚合"处理。但各仓库 LICENSE 要单独看，不能一概而论
Live2D 模型资产 单独授权 开源代码的许可证不覆盖模型文件。要商用需单独确认 Live2D Inc. 条款，或改用 VRM

实操建议：仓库根目录放一份 AGPL-3.0，然后在 README 里写清楚哪部分来自哪个项目、各自原许可证是什么。 这既是合规要求，也是给别人省事——人家一看就知道能不能用你的代码。

07

两个产品，两条独立的线

execution order
第 1 步

产品 A：先跑通 PC 端，再扩到安卓

PC 端骨架已经能跑（25 项测试）。接 NapCat 之后先在群里 dry_run 一周， 只看草稿不发。同时把 necessity 的沉默率调到你觉得舒服的位置——这个参数比话术更影响"像不像"。

第 2 步

产品 A：安卓端只做「草稿 + 确认」

把 app/android/ 补进 Android Studio，先适配 1 个 App， 校准好选择器。默认 autoSend=false，只用悬浮窗。跑两周看自己是否真的在用。

第 3 步

产品 A：改 AstrBot，开源

适配层和插件层动手，核心层不动。开源前清密钥、重写历史、写好 README 的许可证说明。 这一步的产出本身就能带来用户，比闭源做小工具更容易传播。

第 4 步

产品 B：陪伴应用，基于 AIRI 的 MIT 代码

这条线和 A 完全独立，可以并行。记住 AIRI 官方没有移动端， 安卓端要么把 Web 版做成 PWA，要么补一层 Capacitor 外壳。这一步的工期要按"自己补"来估算。

三句话收尾

  1. 安卓无障碍能做，但"不被发现"这个前提是假的。 包名在系统服务列表里，行为节奏在日志里。降低风险的唯一有效手段是让行为本身不像机器—— 不秒回、有抖动、该沉默时沉默，而不是去研究怎么隐藏。
  2. 交友类平台要先分清用途再谈技术。 心遇这类「回复可提现」的平台，全自动回复的实际效果是用机器骗取分成，性质不是违规。 自用、辅助输入、最终由人点发送，这条路是稳的；批量养号赚金币，我不参与，也建议你别碰。
  3. AstrBot 决定开源之后就是最省力的底座，MaiBot 最该借的是「什么时候不说话」。 AGPL 从约束变成了保证，GPLv3 也能直接吸收进来。改造只动适配层和插件层， 核心层别碰——它的更新频率很高，改了合并上游会很痛苦。
