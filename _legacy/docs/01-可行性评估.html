NEXUS/工作台 文档 01 可行性评估 · 架构方案
调研基于 2025-2026 平台公开规则
Preliminary Assessment / 阶段一判断

两个功能
一个能跑
一个不能

你设想的形态是：一个 APP，内置 AI 接管账号自动回复（微信 / QQ / B站 / Soul / 他趣）， 再内置图文内容生成并自动发布（小红书 / 抖音）来获客。 结论先说：功能 B 能跑通一半，功能 A 在现行规则下跑不通。 下面是把"为什么"拆开讲清楚，以及在不放弃目标的前提下，路该怎么走。

功能 A · 接管账号自动回复 不可行

技术能实现，但微信明文定性为"外挂"，抖音/Soul/他趣无开放接口。作为上架 APP 分发会被拒。

功能 B · 图文获客发布 半可行

小红书走官方 API 可行但需企业资质；抖音 2025-08 起明确排除营销类内容，官方通道关闭。

人设统一窗口 必须做

不仅是"能加"，而是整个产品的架构中枢。人设不统一，每加一个平台就要重写一遍话术。

01

平台能力矩阵

官方公开信息 · 逐条核实

这张表是整份文档的地基。你提到的每一个平台，我按"能不能拿官方接口读消息 / 能不能自动发内容"两栏拆开。 凡是没有官方接口的，剩下的路只有自动化模拟，而这一步直接决定你的产品能不能上架。

平台 官方消息收发 官方内容发布 关键约束
微信个人号 无接口 无接口 《个人账号使用规范》1.2.6 禁止第三方工具自动化操作；安全中心公告直接把"自动回复、自动聊天"列为外挂
微信公众号 / 企业微信 官方 API 图文群发 需认证主体。客服消息有 48 小时窗口限制，被动回复 5 秒超时
QQ开放平台 Bot 官方 API 受限 支持频道 / 群 / 单聊，WebSocket 或 Webhook。但只能以"机器人"身份存在，无法接管你的个人 QQ 号
哔哩哔哩开放平台 需资质 需资质 面向 UP 主与服务商，需资质认证。社区里流传的私信接口靠 Cookie(SESSDATA) 直连内部服务，非官方授权
小红书开放平台 受限 笔记发布 创作者须完成资质审核（企业或个体户持营业执照）。笔记发布权限另行审核，需说明具体场景

02

功能 A：接管账号自动回复

三个层面，三种答案

"能不能跑通"这句话在技术圈和法务圈是两个完全不同的问题。我把它拆成三层， 因为你这三层里只要有一层过不去，产品就落不了地。

Layer 1 · 技术
可行
  • Android 无障碍服务（AccessibilityService）能跨 App 读取界面节点、模拟点击与输入
  • 通知监听（NotificationListenerService）能拿到消息推送内容
  • 上述两项在安卓上不需要 root，是正规系统能力
  • 结论：单个设备上"看到消息 → 生成回复 → 填入输入框"完全能做到
Layer 2 · 合规
不可行
  • 微信把"自动回复、自动聊天"直接点名归为外挂
  • iOS 无跨应用界面注入能力，这一半市场天然不存在
  • 小红书 / 抖音 / Soul / 他趣 用户协议均禁止自动化访问
  • 结论：只有 QQ Bot 与微信公众号是"被授权"的自动化
Layer 3 · 商业
不可上架
  • 应用商店审核规则普遍拒绝"修改/接管第三方应用"类功能
  • iOS App Store 直接拒审，无法双端发行
  • 一旦规模做大必然收到平台律师函，商业模型随时归零
  • 结论：不能作为主线产品，只能作为小范围实验功能
微信安全中心《针对在微信使用"外挂"行为的打击公告》原文列举的常见外挂类型中包含： "微信机器人：微信群营销，实现定时群发、自动回复、自动聊天等控制功能。" 处理方式是"根据违规严重程度进行阶梯式处理；对于多次违规者，将加重处罚"。 — 腾讯 · 微信安全中心公开公告

所以哪些真的能跑

场景状态说明
QQ 群 / 频道 / 单聊 AI 机器人 可上线 官方 Bot API，WebSocket 长连接，个人主体可创建，认证后进群上限 500
微信公众号 / 企业微信客服自动回复 可上线 官方客服消息接口，需认证主体，注意 48 小时会话窗口
AI 辅助回复（生成 → 人工确认发送） 可上线 界限在于"最终发送动作由人完成"。可用快捷回复面板 / 剪贴板 / 输入法实现
微信个人号全自动接管 高风险 技术上能跑，违规。仅可作为不上架的实验室模式，需用户显式确认风险
Soul / 他趣 自动回复 不建议 无接口、风控极严、账号成本高，投入产出不成立
03

功能 B：图文获客发布

拆成三段看，只有中间那段卡住

这个功能其实包含三件事：读懂图片 → 写出文案 → 发出去。前两件没有任何平台限制， 只有第三件被平台规则卡住。所以正确做法是把它切成"可全自动"和"必须半自动"两段。

Layer 1 · 图片理解与文案生成
完全自由
  • 多模态模型读图、提取卖点、识别场景，无平台约束
  • 按平台调性改写（小红书种草体 / 抖音口播脚本）
  • 这是你真正的产品壁垒所在，也是最该重投的部分
Layer 2 · 自动发布
分平台
  • 小红书：官方笔记发布 API 可用，但需资质审核
  • 抖音：2025-08 新政明确不向营销场景开放，通道关闭
  • 视频号：需走微信生态，个人主体无发布 API
Layer 3 · 获客转化
产品机会
  • 发布只是起点，真正值钱的是"谁看了、谁私信了、谁留了联系方式"
  • 把这部分做成线索台账，产品价值立刻从工具变成资产
  • 这也是竞品普遍缺失的一环
抖音开放平台 2025 年公告原文：应用主体"不再向个体工商户类型主体开放"；企业需满足"注册资本 ≥50 万且注册时间 ≥1 年"； 应用类型"仅对创作工具、社区、硬件配套、游戏类应用开放"； "如涉及企业宣传、商品介绍、诱导分享等营销类内容分享，将不开放该能力准入。" — 抖音开放平台 · 发布内容至抖音能力回收与开放规范调整通知

这条规则的言外之意很清楚：抖音欢迎"帮用户把自己的作品发出去"，不欢迎"帮商家把广告发出去"。 你的场景属于后者。所以抖音这条路上，唯一成立的产品形态是 生成好内容 + 一键跳转抖音 App 由用户自己点发布——本质上是把自动发布降级成"极省力的人工发布"。 体验损失很小，合规风险归零。

04

三条可选路线

按推荐度排序

既然原方案跑不通，目标不能丢——你要的是"AI 帮我把聊天和获客这两件重复劳动干掉"。 下面三条路都能通向这个目标，区别在于风险敞口和发行渠道。

01
AI 副驾模式 推荐主线

APP 不代替你发消息，而是把回复写到你能一键取用的地方：通知栏快捷回复、悬浮球面板、 系统输入法词条。AI 生成 3 个候选回复，你点一下即发送。 合规边界清晰——最终动作是人做的。可正常上架双端应用商店。

合规 · 高 上架 · 可 体验损失 · 小
02
官方通道矩阵

只接有官方接口的渠道：QQ Bot、微信公众号 / 企业微信客服、小红书企业号。 全部走授权 API，稳定性与规模化能力最强，且能做到真正的全自动。 代价是覆盖面小于你的初始设想，且需要企业主体。

合规 · 最高 上架 · 可 门槛 · 企业资质
03
实验室模式

个人号接管做成独立模块，不做应用商店分发（侧载 / 桌面端），首次启用强制阅读风险告知并二次确认。 功能完整但风险由用户承担。适合自用或小范围灰度，不适合作为商业主线。

合规 · 低 上架 · 否 定位 · 自用

我的建议：主线走 01，能力补 02，03 只做可选实验区。 这三条路共用同一套底层（人设 + 回复引擎 + 内容工厂），所以不存在"做了 A 就不能做 B"的问题—— 差别只在最上面那层渠道适配器。这也是下面板块拆分的设计前提。

05

板块拆分：七层架构

从下往上，越往上越容易被平台卡

拆板块的正确方式不是按"功能"切（自动回复一块、发内容一块），而是按"变化频率"切。 越容易变的放上面，越稳定的放下面。这样新增一个平台只是加一个适配器，不用动引擎。

L7控制台CONSOLE · APP 前端
五个一级页面：会话 / 获客 / 人设 / 渠道 / 我的。所有数据来自下层，自身不存业务状态。
L6渠道适配层CHANNEL HUB · Adapter
每个平台一个适配器，把平台原始消息统一成内部 Message{ch, sender, text, media, ts} 事件。 新增平台 = 新增一个文件。这是整个架构里最关键的解耦点。
L5风控闸门GUARD · 不可省
频控（每分钟/每小时条数）、敏感词、承诺类话术拦截、人工确认率、渠道健康度熔断。 这一层看着不产生价值，但它是产品能活过三个月的唯一原因。
L4能力层CAPABILITY · 无状态
两个并列能力：回复引擎（读上下文 → 草稿）与内容工厂（读图 → 文案 → 平台改写）。 都是纯函数式的：输入上下文，输出草稿，不自己发出去。
L3人设中枢PERSONA · 一等实体
所有渠道、所有能力共享同一份人设资产：身份、语气、知识库、边界、示范语料。 支持按渠道微调覆盖。这就是你问的"人设设置窗口"在架构里的位置。
L2调度层SCHEDULER · 队列
任务队列、限速、失败重试、定时发布、延迟回复（模拟人类节奏，避免秒回被判定为机器人）。
L1数据层LEDGER · 持久化
会话记录、人设配置、内容草稿、发布记录、线索台账。获客功能的商业价值全部落在这里。

映射到 APP 的五个一级页面

TAB 01

会话 Inbox

全渠道消息聚合。左侧平台筛选，中间对话流，右侧 AI 建议三选一。人工接管按钮常驻。

TAB 02

获客 Acquire

上传图片 → 生成文案 → 选平台 → 进发布队列。下半屏是线索台账：谁来过、留了什么、值多少。

TAB 03

人设 Persona

多个人设卡片管理 + 编辑面板 + 试衣间（左边改参数，右边实时对话预览）。详见下一节。

TAB 04

渠道 Channels

平台连接状态、授权有效期、今日配额消耗、健康度评分、风控告警。

TAB 05

我的 Settings

风控阈值、人工确认率、订阅、实验区开关（实验室模式的风险告知在此）。

06

人设统一窗口

不只是"能加"，而是第一优先级

直接回答你的问题：能加，而且这是整个产品最该先做的东西。 理由很实际——如果人设不统一，你在 B站练出来的二次元语气、在小红书练出来的种草话术、 在微信练出来的客服口吻，会变成三份互不相干的提示词。改一次要改三遍，加一个平台又要再抄一遍。 人设做成独立实体之后，这变成"改一处，全渠道生效"。

人设卡的数据结构

模块内容为什么需要
身份 Identity 名称、头像、年龄、职业、所在地、一句话简介 决定 AI 的世界观。缺了这块，回复会变成没有立场的客服
语气 Voice 正式度、句长、emoji 频率、口头禅、标点习惯（用不用句号） 用滑块与标签而不是自由文本，因为"语气活泼一点"这种描述模型读不懂
知识 Knowledge 产品信息、价格表、FAQ、活动规则，结构化条目 这是防幻觉的唯一手段。自由文本知识库必然被编造
边界 Boundary 不聊什么、不能承诺什么、哪些词必须转人工 比"禁止说脏话"更重要的是"不许承诺效果、不许报价、不许答应退款"
示范 Few-shot 8–15 组「对方说 → 我应该回」，可直接从真实聊天记录里导入 决定像不像人的从来不是形容词，是这几组样例。收益最大的一栏
渠道覆盖 Override 同一人设在 B站 / 小红书 / 微信 的局部微调 让"统一"不等于"机械一致"，各平台仍保留语感差异
设计判断：绝大多数同类产品的失败点，是把人设做成了"一个多行输入框让你写提示词"。 用户写了 200 字的角色描述，AI 还是回得像客服。正确做法是把编辑界面重心从"形容词"移到"示范语料"—— 让用户填 10 句真实对话，比让他写 1000 字人设有效得多。所以人设窗口的默认页签应该是「示范」，不是「身份」。 — 架构建议

试衣间（Sandbox）

人设编辑面板必须有实时预览：左侧参数改动，右侧立刻用新参数生成一条回复。 没有这一步，用户只能"改完保存，去真实聊天里试，发现不对再回来改"—— 这个循环一次要几分钟，用户第三天就流失了。

07

关于直接搬 GitHub 代码

抄架构，别抄代码

你提到去 GitHub 找现成实现来省时间。这个思路对，但需要说清楚：我搜到的主流项目， 搬到"移动端 APP"这个目标上可用度很低。原因不在代码质量，在运行环境根本不同。

主流项目类型运行环境迁移到你的 APP 的问题
wxauto / pywechat 系 Windows 依赖微信 PC 客户端的窗口控件树（UIAutomation）。手机上没有 PC 微信窗口，代码完全无法运行
Wechaty 系 Node / 多端 本身只是框架，真正连微信要买 puppet 服务（付费 token），且相关协议通道反复被封，稳定性不可控
Selenium 网页版微信 浏览器 网页版微信早已对绝大多数账号关闭登录入口，这条路 2021 年后基本失效
LangBot / 机器人编排框架 容器 这个值得看，但要看的是它的平台适配器抽象与消息队列设计，不是它的微信号连接方式
官方 SDK（QQ Bot / 小红书） 任意 这类可以直接用。官方文档 + 官方 demo 是最好的起点，没必要自己造

实操建议：底层通用组件直接装包（图片理解、文案生成、队列、本地数据库）， 平台连接层自己写适配器。因为适配器是你唯一能形成差异的地方，也是最容易出安全问题的地方， 用别人的黑盒代码，出问题你连日志都看不懂。

08

落地路线

四个里程碑，每个都能独立验证

不要一开始就做"五平台支持 + 全自动发布"。先用人设 + 单一渠道跑通闭环， 验证"AI 写的回复用户愿意直接发出去"这件事，再横向扩渠道。

MILESTONE 01

人设中枢 + 单渠道

  • 人设卡 CRUD 与试衣间
  • QQ Bot 单一适配器
  • 回复引擎接入，草稿三选一
  • 验证指标：草稿采纳率 ≥ 40%
MILESTONE 02

内容工厂 + 半自动发布

  • 图片上传与多模态读图
  • 多平台文案改写
  • 草稿箱与分享跳转
  • 验证指标：从上传到可发布 < 3 分钟
MILESTONE 03

风控闸门 + 线索台账

  • 频控、敏感词、熔断
  • 线索归集与打标
  • 渠道健康度看板
  • 验证指标：零封号 / 零投诉
MILESTONE 04

渠道横向扩张

  • 微信公众号 / 企业微信
  • 小红书企业号发布
  • B站适配器（如资质可行）
  • 验证指标：新增渠道零改造引擎

四句话收尾

  1. 功能 A 在现行规则下跑不通，别把它当主线。 技术能做到，但微信已把"自动回复、自动聊天"明文列为外挂，抖音无接口，Soul 与他趣不开放，iOS 端物理上做不到。 作为上架 APP 的内置功能，它在审核环节就会被拦下。
  2. 功能 B 能跑，但要切成两段。 读图 + 写文案完全自由，是真正的技术壁垒；自动发布只有小红书官方通道一条路，抖音 2025-08 起已明确排除营销场景。 半自动发布（生成好 + 一键跳转）体验损失很小，风险归零。
  3. 板块按"变化频率"拆成七层，不是按功能拆。 渠道在最上面（天天变）、人设在中枢（最稳定）、闸门在中间（决定生死）。新增平台只加适配器，不动引擎。
  4. 人设统一窗口不仅可行，应该第一个做。 它是把"三个平台三份提示词"变成"一份资产全渠道生效"的唯一办法。 设计上把重心放在示范语料而不是形容词，并配一个实时试衣间。
