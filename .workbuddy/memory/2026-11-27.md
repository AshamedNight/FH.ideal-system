## "生成和下层日志对不上" —— 三个不同的原因，不是一个

用户截图（他趣）：判定链写 `④ 生成：第 1 次成稿`、草稿「刚忙完，累得不想动。你忙不忙」、
`填入：已通过输入法写入`，但下面「草稿」行是「换个话题吧」；
而且 `本次：输入 0 / 输出 0 token`、`本地估算：约 0 token 输入`。

关键判据：**本地估算也是 0** → 这一轮根本没构造请求。走的是
`ReplyEngine.generate()` 里"开场白 / 话术库"那条：`greetingEnabled && !iSaidAlready && peerOpenedWithGreeting`
时直接返回库里的句子（tokens 0、attempts=1），但判定链只写"第 1 次成稿"，不写来源。

另外两层"对不上"：

1. 上层那块是 **MainActivity「试填」的历史结果**，不会跟着输入法面板的动作刷新；
   下层「草稿」是输入框**实时**内容。两张纸来自不同时刻。
2. `commitText` 只写进"当前绑定的 InputConnection"。面板/首页浮在目标 App 上时
   这个连接可能还连着上一个输入框 → 写进别处、目标框还是旧内容，日志却报"已写入"。

修了四处：

- `ReplyEngine.Result.Draft` 加 `source`（模型 / 话术库 / 开场白（多条）/ 开场白库 / 演练），
  由 `sourceLabel()` 判定 mock；`ReplyFlow` 的 ④ 变成 `第 N 次成稿 · 来源 X`。
- `AutoReplyImeService` 记 `boundPkg`（onStartInputView 取 `info.packageName`），
  `commit(text, replaceFirst, expectedPkg)` 先比包名：不一致就**挂起**（pendingPkg）不硬写；
  `flushPending` 也按 pendingPkg 拒绝串到别的 App。
- `TextWriter` 传 `expectedPkg`，包名不符时给出准确提示「先点一下这个 App 的输入框」。
- 试填输出头加时间戳 `判定链（试填 09:39:12）`；面板生成后 250ms 再刷一次草稿行
  （commitText 的 selection 回调有时比回调晚一拍）。

教训（值得复用）：**日志里"0 token"要能和"没调模型"对上号**。
只要 UI 上有"成稿"这种中性词，用户就会默认是模型写的，然后拿它去和别处对账。
凡是"本地库/快捷路径"，输出必须自报家门。

## 多行输入框在 ScrollView 里划不动（通用坑，已修）

现象：设置页「开场白库」填了十几条后，框里内容超出可视高度，**既看不全也滚不动**。

根因不是"框太矮"，是事件分发：`EditText` 嵌在 `ScrollView` 里时，
手指一落在框上，外层 ScrollView 直接在 `onInterceptTouchEvent` 里把滑动抢走，
`EditText` 自己的滚动永远收不到。

修法（两页共用同一套）：
```kotlin
setOnTouchListener { v, e ->
    when (e.actionMasked) {
        ACTION_DOWN -> v.parent?.requestDisallowInterceptTouchEvent(true)
        ACTION_UP, ACTION_CANCEL -> v.parent?.requestDisallowInterceptTouchEvent(false)
    }
    false   // 必须 false，否则 EditText 自己也收不到事件
}
```
**只对多行框生效**：单行框也这么干的话，手指落在任何一行输入框上页面都划不动。

落点：
- `SettingsActivity.editBase/field/multi` → 新增 `EditText.scrollableInside()` 扩展；
  `field(singleLine=false)` 从 `maxLines=6` 改成 `minLines=4 / maxLines=8`。
- `PersonaActivity` 同样加了扩展（「我是谁」12 行、准则框 3 行都吃到了）。
- 开场白库再加一个「全屏编辑」按钮：`fullScreenEdit()` 弹接近全屏的对话框，
  改完回填原输入框，保存逻辑不变 —— 卡片里给多高都不够看第 13 条。

## "聊长了回复对不上"：两个真凶

### ① 记忆接缝只认"最后一条"，用户翻历史就被判成换人

原来 `ConversationMemory.merge` 只拿 `cached.last()` 当锚点：找到就追加，**找不到就整段重置**。
用户在聊天页往上翻了一下（很常见：想确认刚才说了什么），这一屏就全是旧消息 →
锚点不在里面 → 记忆清零 → 上下文瞬间倒退十几分钟 → 生成答非所问。

新算法（顺序即优先级）：

1. **尾部重叠**：`cached` 最后 k 条 == `fresh` 前 k 条（k ≤ 6）→ 追加 `fresh[k:]`。
   正常续聊就是这种形状。上限 6 是因为同一句话会被说好几次，比太长容易对齐到更早那次。
2. **旧窗口识别** `isOlderWindow`：`fresh` 每条都能在 `cached` 里**按顺序**找到 →
   认定"用户在翻历史"→ **返回 cached，什么都不改**。这是本次修复的核心。
3. **锚点**：`cached.last()` 出现在 `fresh` 中间（屏幕一半旧一半新）→ 追加它后面的。
4. 都不成立 → 重置（宁可丢，不接错人）。

验证：`tools/verify_memory_merge.py` 用 Python 复刻同一套判定，跑 7 种窗口形状
（正常续聊 / 窗口滑动 / 翻历史 / 换人 / 顶部多一条 / 重复句 / 同文不同向），已接入
`precheck.sh` 第 10 步。**改 Kotlin 必须同步改这个脚本**，否则会变成假通过。

### ② 记忆能存 40 条，但只给模型 12 条

`CONTEXT_TURNS=12` + `OLDER_TURNS=6`（每条截 16 字）。中间那 20 多条几乎白存。
12 → 16、6 → 10：每轮多约 210 token（几分钱），换"接得上"很值。

### 顺带：让"上下文条数"可见

`CaptureService.lastContextTurns`（companion 变量），`ReplyRunner` 在 merge 后写入，
输入法面板状态栏显示 `已写入（未发送）· 上下文 12 条`。
草稿不对时先看这个数：3 条=读少了（长按复制再「换一句」），12 条=上下文够，问题在别处。

用户还问"回复不对应时要切回去再切回来很麻烦" —— 待确认具体指什么（换 App 看聊天？还是
面板挡住看不到）。面板的「换一句」本身就是"重新读屏 + 重生成 + 覆盖上一段"，理论上不需要切走。





## 自己打字 / 语音：面板加「换键盘」「说一句」

用户澄清了痛点：模型写的不对，但他自己有话说 → 切回系统键盘打字 → 打完再切回来，
一来一回两次切换，比打字本身还累。

两条路都做了：

1. **换键盘**：`InputMethodService.switchInputMethod(id)`（API 28+）直接切到
   `enabledInputMethodList` 里第一个非本包的输入法；27 及以下退回 `showInputMethodPicker()`。
   回来靠系统键盘上的地球图标（我们已注册为可用输入法）。
2. **说一句**：`android.speech.SpeechRecognizer`（系统服务，零依赖），识别结果
   `commit(text)` 直接落进输入框。

**关键取舍**：不能用 `ACTION_RECOGNIZE_SPEECH` 那个系统识别界面 ——
它会拉起 Activity 抢走焦点，输入法此时已无 InputConnection，识别完写不回去，
只能挂起等用户再点一次。SpeechRecognizer 是我们自己起自己收，不切界面。

配套：
- Manifest 加 `RECORD_AUDIO` + `<queries>` 的 `android.speech.RecognitionService`
  （Android 11+ 不声明的话 `isRecognitionAvailable()` 恒 false，表现为"点语音没反应"）。
- 权限必须由 Activity 要：面板没授权时带 `ask_mic` extra 跳 MainActivity，
  `requestPermissions(RECORD_AUDIO)`；回来再点「说一句」。
- `onDestroy` 里 `recognizer?.destroy()`，避免输入法被换下时泄漏。

待真机验证：不同 ROM 的语音服务可用性差异很大（国产机多为厂商云端识别），
没有识别服务时给的是"这台机器没有语音识别服务 —— 换键盘自己打吧"。

## 语音：真机报"没有语音识别服务"

`SpeechRecognizer.isRecognitionAvailable()` 返回 false。**"键盘能语音"≠"系统有识别服务"**：

- 键盘（讯飞/搜狗/百度输入法）的语音按钮是**键盘自己接的云端 SDK**，不经过系统 RecognitionService；
- `SpeechRecognizer` 找的是实现了 `android.speech.RecognitionService` 的**系统组件**，
  国产 ROM 大多没装，或装了也不导出给三方应用；
- 所以这跟机型强相关：同一 APK 在小米/华为/OPPO/vivo/原生 Android 上结果不同。
  国内几乎没有"可独立安装"的 RecognitionService（Google 语音服务要 GMS，装了也常连不上）。

现状（已做）：
- 设置页「输入法」段加「语音输入诊断」按钮：列出 `queryIntentServices` 找到的识别服务、
  `isRecognitionAvailable`、麦克风权限，并区分三种原因（没装 / 不可见 / 不可用）。
- 面板提示改成可操作路径：**「换键盘」→ 用键盘自带的语音 → 说完切回来**（零成本，现在就能用）。

评估过的"自己做 ASR"，没实施（要用户点头）：
- AudioRecord 16k/16bit 单声道 + 简单 VAD 断句 → wav/pcm → 上传到现有 relay.js → 上游一句话识别
  （讯飞/阿里/腾讯都有免费额度；OpenAI whisper-1 约 $0.006/分钟，每天 10 分钟≈几毛钱/月）。
- 代价：**音频要上传**（与"人设、词表、Key 都在本机"的定位冲突）；还要处理长按说话 UI、
  录音权限、网络失败。工作量约 300~400 行 + relay 加一个端点。

- 点某条事实 → 弹窗改；**留空等于删**；改过的事实 confidence 直接写 1.0（人确认过的就是准的）。
- 低置信（<0.7）在界面上标「不确定」——提示词里不会用它，但要让人知道它记了这么一条。
- 可删整个人（`forget`）、可清空全部（`clear`）。
- **刻意不做"新增"**：事实只能来自对话或人工修改；凭空加一条对话里没出现过的事，
  模型下次会拿它当真话说出去。
- 整页 `render()` 重建（removeAllViews + 重画）：页面状态就是数据库本身，比局部刷新稳。
- 抽错必然发生（`我妹今年28` → "她 28"），所以"能改"是 P1 的核心理由，不是锦上添花。
