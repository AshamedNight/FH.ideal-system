## 他趣通知截断 + 「下一个未读」认不出 + 跨平台乒乓

### 1. 他趣通知只有预览（「…你平时是不是特…」）
通知栏收起态只给一行预览。全文可能在：`Notification.EXTRA_MESSAGES`（MessagingStyle，

**改法**：三个来源都读，取最长；昵称优先用 MessagingStyle 的 `sender`。
若三者都短，那就是通知本身被截断，取不到 —— 只能读聊天页或 OCR，不要承诺。

### 2. 「下一个未读」认不出 → 连点不往下走
真机截图里那个是**纯图标圆形按钮**（红点 + «»），`text` 为空。
而心遇配置只有 `textContains "下一个未读"`、同城是 `viewId tv_next` ——
心遇那条必然失败；同城那条如果 id 改版也会失败。
**改法**：
- `Selector` 新增 `contentDescContains`（图标按钮的唯一线索常是无障碍描述）
- 两个平台 nextUnread 都扩成四级：viewId → 文字 → 描述含「下一个」 → 文字「>>」
- 心遇补 `viewId tvUnreadRemind`（老 dump 里就是这个 id，文字是"下一个未读>>"）

### 3. 两个平台之间来回弹
`platformHops` 有上限但会让"心遇→同城→心遇"发生一次。
**改法**：加 `visitedPkgs`（每轮连点清空），绕回已去过的平台直接 `stopBatch` 并说明原因。

### 4. 读空没线索
`NodeQuery.emptyDiagnosis()` 一句话写出「选择器没命中 / 全树 N 个节点 / 前几个带文字的 id」，
`ReplyRunner` 在读空时 `service.logAuto(...)`（`logAuto` 因此从 private 改 public）。
他趣这种 `profile.message` 为空的平台则直接提示"只能等通知触发"。

**待验证**：通知全文是否真能拿到（MessagingStyle 不一定有）；

## 真凶：canPerformGestures 一直是 false（这一条要记住）

`app/src/main/res/xml/accessibility_service_config.xml` 里原本写死
`android:canPerformGestures="false"`，注释还解释了理由（不注入伪造触摸轨迹）。
后果：**`dispatchGesture` 永远失败**，`TextWriter.tapNode()` 静默返回 false，
所有"按坐标点"的兜底从来没生效过。

于是 `clickNextUnread` 只能走 `performAction(ACTION_CLICK)`；
同城 `#tv_next` 是自定义 View，它**返回 true 但界面不动**（框架派发了，业务没接）。
表现：日志「点了「下一个未读」但会话没换」→ 程序以为切走了 → 在同一个会话里
再生成一遍 → 用户看到"不往下走 + 重复生成"。

**已改 true**，理由写在配置注释里：这个按钮是全项目唯一主动点击的东西，
而"点下一个未读"本来就是真人天天做的动作；滑动仍然用 ACTION_SCROLL，不注入手势。

⚠️ **改这个配置必须让用户把读屏服务关掉再打开一次**（或重启），否则不生效。
为此在 `clickNextUnread` 里加了 `onNote`：触摸派发失败时日志会写
「触摸派发失败（手势权限没生效？）」—— 看到这句就说明没重开服务。

## CI 编译失败：加参数把尾随 lambda 顶掉了

`clickNextUnread` 加了第 4 个参数 `onNote: ((String) -> Unit)?` 之后，
`MainActivity` 里的旧写法 `clickNextUnread(root, profile) { node -> ... }` 编译失败：

```
Type mismatch: inferred type is String but AccessibilityNodeInfo was expected
```

原因：**Kotlin 的尾随 lambda 永远绑到最后一个参数**。原来最后一个参数是 `tap`，
加了 `onNote` 之后 lambda 就变成"给 onNote 传的"，参数类型从 node 变成 String。

**规矩（记下来）**：往这类"最后一个参数是回调"的函数里再加参数时，
所有调用点都必须改成**命名参数**；或者把新参数插在回调**之前**。
这个项目和上一次的 `label()` 改名漏改是同一类问题 —— 签名改动的影响面靠 grep 调用点算不准。

已修：两个调用点（CaptureService / MainActivity）都写成 `tap = { ... }`。

**顺带**：`canPerformGestures=true` 之后，`TextWriter.tapInputBox`（点输入框容器拿焦点）
也终于真的能用了 —— 它之前同样是静默失败的。

## 分发授权：中转（relay/）已落地

用户要求三条：①超额当天停用 ②其他设备的 key 隐藏不可复制 ③本机决定是否上调别人额度。
**结论：三条都必须在服务端，客户端一律可绕。** 关键说法是"分发版干脆没有 key"——
设备只持令牌，真实 key 只在中转里；不存在的东西偷不走。

**用户问 Termux 能否当服务器 → 可行**，且逻辑上更干净（信任边界落在 master 手机上，
admin 通道就是 localhost，连鉴权都省了）。但工程上有三个硬伤，已如实告知：
1. 可达性：运营商 NAT 后面，必须穿透
2. 进程存活：`termux-wake-lock` 只管 CPU，不管国产 ROM 清后台；要电池白名单 + 锁后台
3. 稳定性即体验：master 手机关机/断网 = 全员不可用，且用户不知道原因

**已写并验证**：
- `relay/relay.js` —— 单文件零依赖（http/https/crypto/fs）。按 deviceId 计日额度，
  429 带中文说明；**上游非 2xx 不计数**（否则用户觉得"什么都没得到却少了额度"）。
  token = `id.HMAC(secret,id).slice(0,32)`；`AUTH_MODE=open|signed`。
  admin 接口只认 `127.0.0.1`。
- `relay/selftest.js` —— 假上游 + 子进程起中转，**25 项断言全过**（无令牌/伪造/放行/
  失败不计数/超额 429/多设备隔离/调额恢复/签名签发）。
- `relay/start-termux.sh`、`relay/README.md`（含五条穿透路线对比）。

**穿透方案的关键判断**（写进 README）：
- Tailscale 最稳，但会让系统出现 VPN，交友 App 可读 `TRANSPORT_VPN` 并标记 → 风控有代价
- Cloudflare Tunnel 无副作用但国内不稳（否 workers.dev 是同一个理由）
- 花生壳/natapp 国内稳、免装客户端，最贴合"不买服务器"

## 爱聊 dump 实测：`w.root` 可读，问题只在"没登记包名"

用户贴的抓取结果（20:28，爱聊聊天页 + 我们的面板浮在上面）：

```
# 3 APP com.autoreply.app [328,443,1048,1643] active focused
# 4 APP com.mosheng     [0,0,1080,2400]
```

**判据**：`describeWindows()` 里包名是 `w.root?.packageName ?: "?"` 读出来的，
打出 `com.mosheng` 而不是 `?` → **根节点非空、可读**。所以他趣那种"整树 noimp"
在爱聊这里不成立（至少根层不是）。报"还没抓到界面"只有一个原因：
`isTarget("com.mosheng")` 为 false —— 装的旧包 `profiles.json` 里没有这一段，
目标应用包名里也没填（`isTarget = list.contains(pkg) || configured`）。

**不用等新包的验证路径**：设置 → 目标应用包名 加一行 `com.mosheng` → 回聊天页抓取。
（以后接新平台同样适用：先加包名抓 dump，再写选择器。）

**顺带补的兜底**（CaptureService.snapshot）：targetRoot() 为空时，
抓**面积最大的、非本 App、非 systemui 的 TYPE_APPLICATION 窗口**，
头部注明「未登记的平台：pkg」+ 怎么登记；**不写入 cachedDump**
（缓存代表"这个平台的树"，混进别的 App 会误导后续判断）。
`hint_no_dump` 同步改成"屏幕上没有可读 App 窗口 + 去加包名"。

**待做**：等用户按上面路径抓到爱聊聊天页 dump → 补 message/messageList/input；
若消息可读且输入框可写，把 `clipboardPreferred` 改回 false
（剪贴板模式多一步手动，只在真抓不到时才值得）。

**另一个有用的性质**：面板窗口是 active focused，所以 rootInActiveWindow 是我们自己；

## 爱聊 dump 到手：做成常规平台，不用剪贴板

dump（1080x2400，聊天页，182 节点 / 可编辑 1 / 被标不重要 112）关键行：

```

  TextView #left_iv_text "哈喽" [165,1175,371,1328]
  TextView #system_info "🔷爱聊猫发现你俩今天很有缘~…"

FrameLayout #unread_msg_view [952,1715,1047,1787] click  → #tv_tips "下一个未读"
TextView #textTitle "bxgz" click
```

**三处 Kotlin 改动**（都是通用能力，不是爱聊专用 hack）：

1. `Selector` 新增 `viewIdIn`（逗号分隔多 id 一条匹配）。原因：`readMessages`
   **命中第一种选择器就 break**，左右气泡 id 不同（`left_iv_text` / `right_tv`）
   拆成三条也只能拿一侧；拿不到"我发的"→ SentTracker 数我方条数恒 0 →
   配额不涨、断句不推进。
2. `NodeQuery.readMessages` 方向判定：**id 前缀 `left_`/`right_`/`mine_`/`other_`
   优先于坐标**。`#right_tv` 收起态 bounds 是 `[24,1201,24,1266]`（宽 0），
   说明右气泡左边缘不保证落在屏幕右半边，纯坐标会翻车。
3. `CaptureService.snapshot()` 未登记平台兜底（见上一条）+ `hint_no_dump` 文案。

**爱聊配置**：messageList `#list`、message `viewIdIn left_iv_text,right_tv,left_tv`、
input `#editText`、pageHint `#editText`/`#recyclerView_quick_msg`、peerName `#textTitle`、
nextUnread `#unread_msg_view`、`clipboardPreferred:false`。
exclude 加「爱聊猫」「别错过缘分」「已真人认证」「已实名认证」等。
**按 id 精确匹配，所以 #list 里的基本资料卡片 / quick_msg 快捷语都不会被当消息。**

**验证**：`profiles.json` 里所有 viewId 都在 dump 里存在（脚本核对，缺 0 个）；
用真机 bounds 复刻方向判定（哈喽 → fromOther=true；假设右侧 → false；hidden 宽 0 被跳过）；
precheck 8 步全过。

**仍待真机确认**：我方可见气泡（`#right_tv`）的真实 bounds —— 已用 id 前缀兜住，
