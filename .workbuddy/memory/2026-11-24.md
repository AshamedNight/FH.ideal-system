用户推上去后 Kotlin 编译失败，报的是：

**修复**：删旧的那份，把两段注释合成一份（保留"只给模型请求用、分发模式强制清空"）。

**新增 precheck 第 9 步 `tools/check_dupes.py`** —— 这类错误前 8 步一条都查不到：

  改成参数表跨行时按行号当唯一键（宁可漏报）。

## 但真正让 CI 挂的不是重复声明 —— 是注释里写了个「斜杠星号」

修完重复声明再推，CI 报错一行没变。截图底部那条被裁掉的错误才是关键：

```
e: AppConfig.kt:484:1 Unclosed comment
```

**真因**：我在 `dist` 的 KDoc 里写了「precheck 第 5 步本来就会校验 assets/星号json 是否合法」
（原文用的是斜杠加星号）。那一对字符是块注释的开头，而 **Kotlin 的块注释支持嵌套** ——
于是第 26 行又开了一层，从那里到文件尾全成了注释。后果：
- 所有属性都不存在 → 满屏 `Unresolved reference: level / targetPackages / clipboardOnly`
- 类没闭合 → `AppConfig.kt:19:65 Missing '}'`（位置纯属误导，那是解析器停下的地方）
- 文件尾 → `Unclosed comment`

**教训（这次最值钱的一条）**：CI 报「Missing '}'」「Unclosed comment」+ 满屏 Unresolved 时，
第一个该查的不是括号，而是**注释里有没有那个斜杠星号组合**（Kotlin 里它嵌套）。
判据很快：数 `/*` 与 `*/` 的个数，或直接跑 precheck 第 7 步。

**已加进 precheck 第 7 步**（`tools/check_encoding.py` 新增 `scan_comments`）：
按 Kotlin 规则扫全项目，报三类 —— 注释里嵌套开新注释（带上下文片段）、多余 `*/`、
文件尾还有未关闭的层。用坏提交 `39dde80` 验证：精确报出第 26 行的
`assets/…json`（嵌套）。

**踩的第二个坑**：修这行时，我在解释文字里又写了一遍那个组合 → 检查立刻报警，
只好改成「斜杠星号」这种文字描述。**这个组合在注释里就是禁区，连解释都不能写。**

## 新功能：聊天记录落盘 + 导出 txt（用户提的，已实现）

用户问"能不能让用户决定回传一份 txt，里面保存这个软件的聊天记录"。结论：能做，
但记的是**程序读到的**，不是真实聊天史。

**关键设计**（三个都是用户选的）：默认关 / 记录含草稿并区分 / 30 天自动清理。

- `core/log/ChatLogStore.kt`：按天写 `filesDir/chatlog/YYYY-MM-DD.txt`，零权限。
- **去重用游标，不用内容指纹**：每会话在 SharedPreferences 存「最后一条」(方向+文本前 80 字)，
  下次在新列表里 indexOfLast 找到它，只写后面的。
  **为什么重要**：`readMessages` 每次都返回整段可见对话，按内容去重会把
  对方连发的两个「哈哈」并成一条 —— 那是真消息，不能吞。所以只有"游标失效、
  整段重写"这条兜底路径才用进程内 LRU 去重。
- 导出走 `ACTION_CREATE_DOCUMENT`（SAF）：用户选位置，不申请存储权限。
  全文先在内存里拿好（`pendingExport`），等 onActivityResult 回来再写 URI。
- **两条生成路径都要接**：`ReplyRunner`（自动/面板）和 `MainActivity`（首页按钮）。
  这是本项目反复踩的坑 —— 上次剪贴板模式就漏了首页那条。
- 草稿行标注交付结果（已填入输入框 / 已复制到剪贴板 / 未交付 / 仅草稿不建议发送），
  和「我：…」分开写，这样"哪句是 AI 写的"一眼可辨。

**验证**：用 Python 复刻游标算法跑四种情形（重复读、增量、新进程、对话滚走），
确认「你好/哈哈/哈哈」三条都保留、二次读不重复；precheck 9 步全过。

**边界（写进导出文件头和设置页说明）**：只记读到的会话；语音/图片/表情无文字节点；
时间戳是首次读到的时刻，不是真实发送时间。

## 第三次 CI 挂：`}` 换行接 `!=` 是语法错误，不是类型错误

推上聊天记录后 CI 报：

```
SettingsActivity.kt:450:17 Expecting an element
SettingsActivity.kt:454:17 Type mismatch: inferred type is Boolean? but Boolean was expected
```

我写的是：

```kotlin
val written = runCatching {
    contentResolver.openOutputStream(uri)?.use { it.write(bytes) }
        != null
}.getOrDefault(false)
```

**Kotlin 的换行就是语句边界**：`}` 之后另起一行接 `!=`，解析器已经结束了这条表达式，
下一行的 `!=` 成了非法的语句开头 → `Expecting an element`；lambda 最后的值变成
`Unit?` 之类的平台类型 → 才冒出那条 `Boolean? but Boolean was expected`。
（`?:` 在行首是**合法**的例外，项目里到处都是，不能一起查。）

**改法**：分步写 —— 先 `val out = ...`，null 就 false，否则 `out.use { it.write(bytes) }` 再 true。
比一行流多三行，但没有任何解析歧义。

**已加进 precheck 第 7 步**（`scan_continuation`）：上一行以 `}` / `)` 收尾、
下一行以 `!=` `==` `&&` `||` 开头 → 报。刻意排除 `?:`（Elvis 行首合法）
和以 `*` / `//` 开头的注释行。用失败提交 `cb595ba` 验证：精确报出第 450 行 `!= null`。

**顺带去掉一处不必要的编译风险**：`ChatLogStore.seen` 原来用
`object : LinkedHashMap<...> { override fun removeEldestEntry(...) }`，覆写 Java
protected 方法的签名（`MutableMap.MutableEntry?`）拿不准，改成有界 `LinkedHashSet`
+ 手写淘汰 —— 少一处赌编译器的写法。这次 CI 已经白跑三回，不值得再赌。




## 开场白「多发」：三条自定义，但仍然一条一条发

用户要：勾选后可以自定义开场第一/二/三条。

**关键约束**：不能变成"连发三条"。v0.1.1 已经删掉过一版三句连发 ——
对方还没回就连甩三条，是整套行为里最像脚本的一种。所以设计成：
第一条进输入框，**检测到发出去了才填第二条**（复用 DraftQueue + 发送检测）。

**存储**：三个独立 key（`greeting_multi_1/2/3`）而不是一个多行字段 ——
必须**保留位置**，否则"只填第三条"会顶到第一条，和界面上的位置对不上。
`greetingMultiLines` getter 固定返回 3 项，空串=这条不发。

**穿透改动**：给 `ReplyEngine.Result.Draft` 和 `ReplyFlow.Outcome.Fill` 各加
`parts: List<String>`（已切好的多条）；`deliver` 的切段顺序变成
`parts` → `single` → `SentenceSplitter`。这样用户写的整句不会被按逗号拆开，
而 parts 为空时行为与原来完全一致（老路径零改动）。

**优先级**：勾了多发就用这三条，不再看库；三条全空或全填不上（比如只写了
`{昵称}` 而昵称没读到）→ 回退到库 → 再回退到模型。

**输入法面板**「用开场白」也接了：写第 1 条 + 余下排进 DraftQueue +
`CaptureService.instance?.scheduleNextSegment()`。面板拿不到昵称/原话，
所以带槽位的条目在那里会被跳过（原有规则）。

**剪贴板模式**：没有输入框可自动填，三条会整段复制，
状态行补一句「共 N 条，按行分开发」——否则用户会一次全粘成一条。

**验证**：`tools/verify_greeting_hooks.py` 加【5】组（三条都填 / 只填一条 /
只填第三条 / 昵称缺失整条跳过 / 带槽位替换后无花括号），全过；precheck 9 步全过。

### 心遇：消息节点连 id 都没有

- `NodeQuery.insideNoiseContainer`：祖先里有 `WebView` / `HorizontalScrollView` 就丢 →

### 偶尔分条（burst）

用户要"后续聊天偶尔连发 2~3 条，手动生成也要"。已有一条一条填的 `parts` 通道，
所以只缺"什么时候拆"：
- 每次生成**掷一次骰子**（`burstChance` 默认 30，`burstMax` 2~3），
  掷在 `generate()` 里、循环外 —— 保证同一次生成的多次重试策略一致。
- 命中才往 system 追加「这一次可以分几条发」；**必须给出路**："一句话就能说完就只回一行"，
  否则模型会把每句都硬拆三条，比单条更像脚本。
- 模型用换行分句 → 成功分支里 split('\n') 取前 burstMax 条，≥2 条才走 parts。

### 连点待命

原来"没有下一个未读"直接 stopBatch，于是几分钟后才来的新未读永远等不到。
改成：第一次进入记 `batchWaitStart` 并说明在等；每 10 秒 `batchStep()` 一次；
5 分钟超时才停。`startBatch`/`stopBatch`/点击成功都要清零这个起点。
（注意第一版写错了：把 `batchWaitStart == 0` 当成"已超时"，会一进待命就报"等了5分钟"。）
