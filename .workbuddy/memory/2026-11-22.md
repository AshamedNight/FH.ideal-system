## 「同一句连点生成结果相同」+ 输入框叠加（commit d1d6a7e）

用户截图：输入框是 **「怎么说怎么说怎么说」** —— 三遍叠在一起，状态行还停在上一轮。
两个独立问题叠在一起：

### ① 输入框叠加（bug 级）
`InputConnection.commitText` 是**在光标处插入**，不是覆盖。
`TextWriter.write(replaceExisting=false)` → `ime.commit(text, replaceFirst=false)`，
所以连点三次就是三份追加。

修法：`AutoReplyImeService` 记住 `lastCommitted`，写新草稿前调 `clearOwnDraft(ic)`：
只用 `getTextBeforeCursor` 读回，**只有当框里内容以 lastCommitted 结尾时**才 `deleteSurroundingText`。
- 用户点发送后 App 清空 → `verifyWritten` 把 lastCommitted 置 null
- 用户自己接着打字 → 不满足 endsWith → 一个字不动
满足"连点不叠加"的同时守住"绝不覆盖用户输入"这条底线。

### ② 同一条消息重复生成结果相同
`DrillReplier.reply(persona, last.text, turns.count { it.fromOther })` ——
round 只由"对方说过几句"决定，**同一条消息重复生成时它根本不变**，
`pick()` 的索引也就不变 → 三次都给同一条。

修法：`AppConfig.drillNudge`（每生成一次 +1，持久化），
`pick(pool, seed, round, nudge)` = `(hash + round*7 + nudge*13) % size`；
样例轮换 `sameQ[floorMod(round + nudge, size)]` 也掺进去。
真实模型不需要（每次本来就不同），只在演练分支自增。

### 验算
`tools/verify_drill_pools.py` 加了【3】连点场景：
同一条「你约？一小时两张」+ 同一 round，nudge 0..5 → 6 条全不同；
邀约场景 nudge 0..3 → 4 条全不同。

## 二次招呼重复发开场白（commit 68b2619）

**现象**：聊到一半，对方（或平台「缘分小助手」）又来一句招呼，输入框里又冒出
「突然有点想认识你」。

**根因**（演练模式）：`DrillReplier` 只拿最后一句话查 `few_shot`，
而 `assets/persona.json` 里 `q="你好"` 配了两条**开场型**答案：
「突然有点想认识你」和「在吗？」。已聊过时查表照样命中 → 又把开场白说一遍。
`buildUser` 里那段"二次招呼别自我介绍"的提示只对真模型有效，假模型根本不看提示词。

**修法**：
- `DrillReplier.reply()` 新增 `alreadyTalking` / `peerJustGreeted` 两个参数，
  由 `ReplyEngine` 把算好的 `iSaidAlready` / `peerOpenedWithGreeting` 传进去
  （**不在 DrillReplier 里重写一份 isJustGreeting**，两份判定早晚走偏）
- 一次都没聊过 → 正常查表；已聊过 + 对方只是招呼 → 走 `REJOIN` 池（在呢/刚看到/刚忙完）
- `NodeQuery` 新增 `SYSTEM_SENDERS`（缘分小助手 / 缘分天使 / 丘比特 / 系统消息 / 平台助手），
  **不看长度**直接丢 —— 这类消息以真人气泡形式出现，被当成"对方第一次打招呼"时
  会触发反问开场白，而对方其实什么都没说

**验算**：`verify_drill_pools.py` 加【1b】，连取 4 次都不落在那两条开场样例上。

## 「手动生成和自动都失效」（commit 77d32f7）

用户截图判定链是关键证据：
```
① 平台闸门：通过（本小时 0/600）
② 该不该回：想回但先等（私聊 +0.48；单字 -0.20；总分 0.28）  等 4 分钟再回
```

### ① 第②层没给手动让路（核心 bug）
`respectEnergy` / `respectCooldown` 只放开第①层和第③层，**第②层的
`NecessityJudge.Action.WAIT` 直接 `return Outcome.Wait(...)`** ——
所以手动点「生成并填入」也纹丝不动。界面上看就是"程序坏了"。

修法：`ReplyFlow.decide()` 新增 `manual` 参数，WAIT 分支在 manual 时只写 trace 放行。
边界：**内容类判断不让路**（SILENT / 话术风险仍拦）—— 那是"说错代价大"，不是"时机不对"。
调用处：`ReplyRunner` 传 `manual || config.drillMode`，`MainActivity` 传 `true`。

### ② 单字统一 -0.20 罚错了对象
「在」是应答，不是敷衍。而真敷衍（嗯/哦/好/行/哈哈/草）在 `FILLER` 正则那步
**早就短路成沉默了** —— 能走到扣分逻辑的单字基本只剩「在/是/对」。
→ 删掉整段单字惩罚。改完「在」= 0.48 ≥ 阈值 0.45 → REPLY。

### ③ 库为空时演练退去 few_shot 拿开场白
截图里设置页开场白库是**空的**，于是走演练 → 查 `q=你好` →
「突然有点想认识你」。用户清空库的本意是"别再发那句"，反被样例接回来。

修法：演练模式 + 库为空 + 开场轮 → 用 `GreetingHooks.DEFAULT` 兜底（抽出 `pickGreeting()` 复用轮换）。
库里有内容时仍以用户的库为准；非演练模式库为空仍交给模型。

**留给用户验的判据**：改后同样的「在」应该显示
`② 该不该回：该回（0.48…）` 而不是「想回但先等」。

## 风控评估：输入法面板化（分析，未实施）

用户问"面板化对风控是提升还是降低"。

**结论：面板本身中性。** 平台只能观测自己 App 内的行为（消息内容 / 时机 / 频率 / 会话数），
输入法是另一个 App 的 UI，平台读不到"在面板上点了几次"。

| 观测面 | 变化 |
|---|---|
| 消息内容 | 不变 |
| 发送频率 | **可能上升**（生成不用切 App，摩擦消失）← 唯一实质风险 |
| 写入通道 commitText | 不变 |
| 前后台切换次数 | **下降**（略降风险：同账号在聊天页反复失焦是弱信号） |

护栏（每小时 15 / 连续 8 / 熔断 30min）都在 ReplyFlow 里，面板只是换个按钮位置，绕不过去。

**三条实施约束**：
1. 跨会话批量动作（连点下一个 / 切换会话）**不要上面板** —— 一键跨多会话是"脚本"的典型形状
2. 发送按钮别配"发完自动生成下一条"，否则节奏变成固定间隔
3. 输入法改名（见下）

### ⚠️ 原本就漏掉的暴露点：输入法的名字

`AndroidManifest.xml` 里 `ime_label = "AutoReply 输入"`、`ime_subtype_label = "AutoReply 写入通道"`。
**任何 App 都能用 `InputMethodManager.getEnabledInputMethodList()`（无需任何权限）**
枚举设备上启用的输入法并 `InputMethodInfo.loadLabel()` 读到这个名字。

也就是说交友 App 完全有能力检测"用户默认输入法叫 AutoReply"。
这跟面板做多大无关，但比面板的风险更实在 —— 建议改成中性名（如「简输入」）。

**AndroidManifest 里没有 `QUERY_ALL_PACKAGES` 之类限制，这条纯靠改名缓解。**

## 输入法面板分两页 + 说话风格（已完成）

**用户拍板：发送不做** —— 用各 App 自带的发送按钮，面板上永远没有发送键。
README「不会替你发送」那句因此不用改口，只在后面补了一句「面板上也没有发送键」。

**分页实现**：`SlidePager`（同文件内的 private FrameLayout 子类）。
- 不用 HorizontalScrollView：页宽要按屏幕宽自己算，分屏/横屏对不齐且不吸附
- `onInterceptTouchEvent` **只在明显横向时**接管（|dx|>1.5*slop 且 |dx|>1.5*|dy|），
  否则网格按钮会点不动；松手按整段位移换页，不看瞬间速度（IME 面板上划动又短又快）
- 两页刻意凑成同样三行，避免换页时面板高度跳变
- 页码存 `AppConfig.imePage`，只在换页时写一次

**风格设计（选了 B 方案）**：`core/llm/TalkStyle.kt` = 5 种（自然/温柔/俏皮/高冷/直接）。
- 没做「给 28 条样例打 style 标签」：以后每加一条都要标，漏标静默失效
- **「自然」的 hint 是空串** → system 提示词一个字不变，老用户升级行为完全一致
- 注入点：`ReplyEngine.buildSystem` 里，**排在 `persona.styleRules` 之前** ——
  后者常含「每句不超过 X 字」这类硬约束，让它后置发声才能压住风格
- 面板第 2 页用 `TalkStyle.ALL.map`，加风格不用改 UI；设置页也加了同一张表的单选
- **演练模式下风格不生效**（假模型不读提示词），面板底部提示会直说
- `chips` 与 `chipOn` 用两个平行 List 而不是塞 `View.tag`：tag 是 Any?，取出要强转，运行时才炸

**验证**：`tools/verify_talk_style.py` —— regex 从 .kt 读风格表，查 id/label 唯一、
DEFAULT_ID 与 AppConfig 默认值一致、非默认 hint 非空且 ≤80 字、hint 不含长度类硬约束、
注入点排在 styleRules 之前、面板没写死风格名。配合 precheck 八步全绿。

## 面板按钮失灵：去重有两层，只修一层等于没修（重要教训）

真机现象：面板能翻页、按钮能点，但点「生成下一条 / 换一句」直接显示
「这条已经处理过（30 分钟内不重复）」，草稿是空的。

**根因**：`ReplyDedup` 的读点有 **两处**：
- `MainActivity.tryGenerate()` —— 上一轮已改成手动放行
- `ReplyRunner.runOnce()` 第 94 行 —— **没改**，而输入法面板走的正是这条路

也就是说"手动越过去重"当初只做了一半。修的时候搜的是调用点，不是**报错文案**。

**修法**：`ReplyRunner` 里 `repeated = dedup.isDuplicate(...)`，
闸门改成 `if (repeated && !manual)`；`deliver()` 加 `replay` 参数，
状态行前缀「手动重来 · 」（面板状态行只显示 28 字，前缀必须短且放前面）。
`CaptureService.alreadyHandled` 那处 `!isDuplicate` **保持不动** —— 那是自动触发，
去重本来就是为它存在的（填草稿→界面变化→再触发 的自循环）。

**可复用的判据**：改"某类动作要不要放行"的逻辑时，
先 `grep` 那句**用户看到的文案**（这里是「已经处理过」），而不是函数名 ——
同一句文案出现几次，就有几道闸门。

## 「发完不自动填下一段」：先确认队列到底有没有东西

真机反馈：发了「刚看到」，草稿变空，没有下一段。

**从截图能读出的事实**：状态行是「已写入 刚看到」，**没有**「（拆成 N 段，发完这段自动填下一段）」
后缀。而 `ReplyRunner.deliver` 里 `segHint` 只在 `parts.size > 1` 时才拼上，面板截断 28 字也放得下 ——
所以这一次回复本来就只有一句，`DraftQueue` 是空的，确实没有下一段可填。
演练模式（没接 KEY）的回复是池子里的**一句**，所以这种"单段"是常态。

**但界面上完全看不出"队列空"还是"卡住"**，这是真缺陷，已修两处：

1. 面板草稿行右侧加「待发 N 段」（空则留白），并且新增 `onUpdateSelection` 覆写来刷新 ——
   原来只在自家动作后刷新，用户点发送后草稿行停在旧内容。
2. `SentTracker.confirmIfSent` 之前是**死代码**。条数判据只读可见区域，发完后旧气泡滚出、
   新气泡滚进会让 `selfMsgs.size` 不变 → 判成"没发" → 配额不涨、连点不推进、下一段不填。
   现在 `sentByText` 作为第二判据（限 pending 90 秒内，避免和历史同款旧气泡混淆）。

**判据留给下次**：让用户看「待发 N 段」。显示 >0 却不填 = 真 bug；显示空 = 本来就没有。

## 连点模式：发完当前消息不推进下个未读会话（真 bug，已修三处）

用户澄清：「下一条」= **下一个会话**（首页那个「下一个未读」），不是断句的下一段。
所以是连点的推进链断了，不是断句。

1. **发送基线只在「真写进输入框」时记**（`ReplyRunner.deliver` 的 `if (write.written)`）。
   走输入法排队 / 剪贴板时 `markPending` + `markBaseline` 都不写 →
   那条消息发出去后 `detectNewSent` 没有基线可比，首次走 `baseCount < 0` 初始化分支返回 false
   → `onBatchSent` 不触发 → 连点不动。已挪到两条通道都记。
2. **找不到「下一个未读」就立刻收工**。刚发完那一下列表在重排，按钮常还不在树上，
   原代码直接 `stopBatch("所有平台都没有未读了")`。现在重试 3 次 × 1.2 秒，
   都失败才换平台/收工（`nextMiss` 字段）。
3. 看门狗（`BATCH_SEND_TIMEOUT_MS = 20s`，注意 KDoc 写的是 45s、常量是 20s）
   跳过时没日志 —— 用户只看到"发完不动"。已补一条说明等了多久。

**另一个结构性风险（未改）**：面板展开会占掉下半屏，RecyclerView 变矮 →
可见的"我发的"条数可能不增不减，`detectNewSent` 的条数判据天然失灵。
这也是为什么同时要 `sentByText`（pending 原文匹配）作为第二判据。

**下次排查顺序**：首页日志里看「等了 20 秒没收到发送信号」还是「没看到下一个未读」
还是「连点结束：所有平台都没有未读了」——三条日志指向三个不同环节。

**下一步（待用户）**：出包后在连点模式下走一遍，看日志落在哪一条。
